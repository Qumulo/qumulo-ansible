Playbooks and roles

The collection ships eleven playbooks in playbooks/ and seven roles in roles/. This page lists what each one targets and does, the variables the playbooks read beyond the inventory’s, the facts and files the roles produce, the edge cache resize route table, the replication restore’s records, files and nine steps, and the replication failover’s states and steps. The task pages say when to run each one: Set up an inventory, Adopt a cluster, Rotate the admin password, License an edge, Size and resize an edge’s cache, Rebuild an edge, Restore a rebuilt edge’s data from its replica, Fail over to a replica, and fail back, Clone an edge’s configuration onto a new edge and Upgrade a fleet. Architecture says how the pieces fit together.

Playbooks

Each playbook in playbooks/ is a worked example, with its usage in its header comment. Run one by name, as ansible-playbook qumulo.cluster.<name>, or copy it as the start of a playbook of your own.

All of them read the connection variables of the inventory (qumulo_api_host, qumulo_api_port, qumulo_api_username, qumulo_api_password, qumulo_api_token, qumulo_validate_certs, qumulo_ca_path and qumulo_cluster_uuid) and hand them to the modules through module_defaults for group/qumulo.cluster.qumulo. edge_license_complete.yml, replication_failover.yml and replication_restore.yml take them from cluster_baseline_connections, which the cluster_baseline role’s tasks/connections.yml records for the edge and for the hosts its relationships target. upgrade.yml connects to qumulo_upgrade_api_host in place of qumulo_api_host when it is set.

No playbook targets the qumulo_hubs group itself. Hubs are in qumulo_clusters like every cluster. The group names the hubs that edges pair with, and a rebuild finds an edge’s hub there.

Files the playbooks write

<artifact dir> is the artifacts directory beside the outermost inventory source on disk that holds the file defining the host, never inside the source. The artifact_dir filter computes it. It is empty for a host that comes from no inventory file, as for -i edge01,. cluster_baseline_artifact_dir, edge_rebuild_artifact_dir and cluster_upgrade_artifact_dir override it for their roles, and replication_pair_artifact_dir defaults to edge_rebuild_artifact_dir. The files capture.yml writes are in Capture and clone and those clone_edge.yml writes in Capture and clone.

The tenancy steps of cluster_baseline

Qumulo marks the multitenancy REST API as preview in Qumulo Core 7.10.3 and 7.11.0. The collection manages tenants through it on those releases, and a later Qumulo Core release may change it.

The role’s tasks/tenants.yml runs steps 3a, 3 and 3b, and tasks/tenants_absent.yml runs step 20a, both included from tasks/main.yml. tenancy_plan, which sends no request, computes what they send.

Step

Runs

2

The ownership check, then, when the inventory declares qumulo_tenants, qumulo_network, qumulo_smb_shares, qumulo_nfs_exports, qumulo_nfs_settings or qumulo_factory_defaults, one read of the cluster and tenancy_plan

Reads the tenants (tenant_info), the network document (network_info), its status only when the cluster has two or more tenants or the run creates one, the shares (smb_info), the exports and the NFS settings and overrides (nfs_info), and cluster_info’s protection type when qumulo_tenants is declared and qumulo_cluster_kind is not. Refuses before any write. When step 3a will write and step 3’s document differs from the cluster’s, checks that document with network_config in check mode. Writes nothing.

The order of 3a, 3 and 3b has its reason in The order of areas. In a check run, tenant and network_config take the planned networks and tenants from the plan, so each write is judged as it will be immediately after it. A tenant that step 3a renames is still under its old name in a check run, so its shares, exports and settings show as creates under the new name.

tenancy_plan is not in the qumulo.cluster.qumulo action group and takes no connection options. A run that passes returns an empty refusals and the items of step_3a, step_3b and step_20a, step 3’s network document with network_changes, bindings and validate, step 18’s smb and step 19’s nfs lists, the tenants that remain, and the continuity verdicts. A run that refuses fails with msg, which holds each refusal’s message on a line, and refusals, each message with the names it gives, such as tenants, networks, entries and the play’s api_host, and nothing else of the plan. At verbosity 3 or more (-vvv) the failure also carries plan, the keys the module had computed when it stopped: none after the renames, the cloud refusal, or the entry, claim and NFSv4.1 rules, the share, export and tenant lists after the network rules, and every key, the network document and its address ranges included, after the continuity rule. Troubleshooting quotes its messages.

Edge cache resize routes

The edge_cache_resize role reads the edge’s file system size, its stored clamp, its license ceiling and its product type, and the edge_cache_route module chooses one route. The role fails when the product type is unknown, or when the cluster does not answer for one of these reads.

The route is the first that applies, in the order of the table. The module compares sizes with a margin, edge_cache_resize_margin_bytes, which defaults to 10% of the target.

Input

Meaning

T

The target, qumulo_capacity.clamp.

R

The stored clamp. unset when none is stored.

L

The license ceiling: the license’s usable capacity cap. On an unprotected edge without a license it is 1 TB. none when there is no ceiling.

C

The file system’s size, which stands in for the provisioned capacity because no API reports it (G-CLAMP-TOL).

floor

edge_cache_resize_floor_bytes, default 1000000000000: what a rebuilt edge provisions at formation, if its platform is larger.

Route

When

What the role does

within

C is within the margin of T.

Applies qumulo_capacity.free_threshold if declared.

below_floor

C is more than the margin above T, and T is below the floor.

Fails unless qumulo_capacity.free_threshold is declared; applies it when it is.

rebuild

C is more than the margin above T, and T is not below the floor.

Fails with the plan to rebuild the edge. With edge_cache_resize_allow_rebuild: true and edge_rebuild_reinstall_tasks, runs the edge_rebuild role with phase all instead, which needs that role’s variables, -e qumulo_rebuild=true and edge_rebuild_eula_accepted among them.

blocked_license

C is more than the margin below T, and L is below T.

Fails. The message names T, the cluster’s UUID, qumulo_capacity.license_document and the edge_license_complete playbook.

platform_limited

C is more than the margin below T, and R already allows T.

Writes no clamp and reports why. Applies free_threshold if declared.

grow

Otherwise: C is more than the margin below T, R does not allow T yet, and L allows T.

Raises the clamp to T with capacity_clamp, which re-forms quorum once, then reads the file system size again. If C is still more than the margin below T, the route becomes platform_limited and the role reports it. Applies free_threshold if declared.

The role prints <route>: <reason> (T=…, R=…, L=…, C=…, margin=…) before it takes the route. With edge_cache_resize_plan_only, which defaults to ansible_check_mode, it prints that and goes no further.

A clamp write re-forms quorum, which pauses the edge, and its portal on its hub, for less than 30 seconds. edge_cache_resize.yml runs one edge at a time. A route that fails ends only that edge, and the last play fails the run naming each edge that failed. A failed automatic rebuild ends the run.

The message of each failing route is in Troubleshooting. The registers explain the routes: G-CLAMP-BOUNCE, G-CLAMP-SHRINK, G-EDGE-FLOOR, G-LICENSE and G-UUID. Licensing and capacity says why provisioned capacity never shrinks, what the floor is, and why a failed automatic rebuild ends the run.

Replication restore

The restore brings back the replicas of a rebuilt edge. For each present relationship out of the edge whose old record on the target, from one of the edge’s qumulo_previous_cluster_uuids, still holds the replica, it syncs the replica back into the edge’s source directory, turns the relationship around and reconnects it, so that it runs from the edge’s current UUID with its declared settings. The replication_pair role’s restore entry point runs it, from playbooks/replication_restore.yml and from the restore play of playbooks/edge_license_complete.yml. The messages of the restore name the records and steps below. Restore a rebuilt edge’s data from its replica has the task and Replication says why a restore keeps X and reverses R.

Records

Name

Is

X

The old record on the target that holds the replica: a live record at the target path from one of the edge’s qumulo_previous_cluster_uuids.

R

The restore relationship, from the target’s replica directory to the edge’s declared source path. Before step 6 its source record is on the target and its target record on the edge. After step 6 it is the other way round, in the declared relationship’s orientation.

The restore record

A file on the controller under <artifact dir>/<edge>/restore/. Step 7 writes it after X’s delete, step 8 marks it before the reconnect, and step 9 removes it.

The restore stamp

A file in the same directory that step 9 writes. It retires the newest rebuild report’s claim on the relationship.

The restore’s files

All of them are under <artifact dir>/<edge>/restore/, with mode 0700 for the directory and 0600 for the files. A record and a stamp are named by the SHA-256 of the relationship’s key: its source path, the target’s UUID in lower case and its target path, each path without a trailing slash. The target host’s name is not hashed. Another controller, or an inventory that adds a trailing slash or renames the target host, finds the same files.

<digest>.yml

The restore record, format: 1: key (source_path, target_host, target_cluster_uuid, target_path), r_id, x_id, x_source_cluster_uuid, x_source_path, x_snapshot_ids, recovery_point, recovery_point_snapshot_id, written_at, and reconnected: true once step 8 has marked it. A record of another format fails the edge’s run, naming the file.

done-<digest>.yml

The restore stamp: format, key, r_id, report, written_at.

lock

The controller’s lock on the edge’s restore. A JSON file, format 1, with the holder, a random token for the run, the controller’s host name, boot id and PID namespace, the ansible-playbook process’s id, its start in clock ticks and its start time, and the lease’s expiry.

lock.guard

The file a takeover or a removal holds an exclusive flock on while it reads the lock again. The file is kept. A run waits at most 60 seconds for it, then refuses.

lock.tmp-<token>

A lock being written. The take removes any older than its lease.

The lock keeps a second restore, or a restore and an upgrade, of the same host from running at once on the same controller. A restore takes it with holder restore, and an upgrade with holder upgrade. It belongs to the controller: two controllers can both restore one edge. A real run takes it before its first step and removes it however the run ends; check mode takes none, and neither does a run whose artifact directory is empty. The lease is the longest the restore of the picked relationships can take: the number of picked relationships times (replication_pair_wait_timeout + replication_restore_reverse_timeout + replication_restore_reconnect_timeout + 600) seconds, plus replication_restore_wait_timeout. The run renews the lock to the full lease before phase 2. Another run’s lock is taken over, with a warning, when its process is gone, if it was taken on this controller (the same host name, boot id and PID namespace), or once its lease has run out, if it was taken on another controller or on one without /proc. A lock whose process is alive on this controller is never taken over. Any other lock refuses, naming its holder, its process, its controller and the end of its lease. A run that is killed leaves its lock. Troubleshooting lists the lock’s messages.

Steps

Phase 1 takes each picked relationship in turn up to step 4, before the next relationship’s step 1. Phase 2 waits for the full syncs together, in rounds spaced replication_restore_poll_delay seconds apart, and finishes each relationship as its sync lands.

Step

Runs on

What it does

1

Edge, controller

Checks that the restore can start (the refusals). Creates the source path and its missing declared ancestors on the edge, and the restore directory on the controller.

2

Target

Creates R on the target: source path the target’s replica directory, target path the edge’s source path, target address and port the edge’s qumulo_replication_address and qumulo_replication_port, enabled, no blackout windows. If the target cannot reach the edge there, nothing is written on either cluster and the restore stops with a hand-off.

3

Edge

Authorizes R on the edge, which waits up to replication_pair_wait_timeout seconds (default 600) until R reads ESTABLISHED on the edge.

4

Edge

Waits for R’s first recovery point, which is the full sync of the replica, up to replication_restore_wait_timeout seconds.

5

Edge

Makes the edge’s directory writable, then waits up to replication_restore_reverse_timeout seconds until R reads DISCONNECTED on the edge.

6

Edge

Reverses R, sending the address and port at which the edge reaches the target: the target’s qumulo_replication_address and qumulo_replication_port. If the edge cannot reach the target there, the reverse fails, neither record changes, and the restore stops.

7

Target, controller

Requires R DISCONNECTED on both clusters. Deletes X on the target, reads R’s record on the target, and writes the restore record.

8

Target

Marks the restore record, reconnects R on the target, and waits up to replication_restore_reconnect_timeout seconds until R reads ESTABLISHED on both clusters.

9

Edge

Applies the declared relationship’s settings to R (replication_enabled, map_local_ids_to_nfs_ids, source_root_read_only, blackout_windows and blackout_window_timezone, as the entry sets them), writes the restore stamp, and removes the restore record.

The restore sets no blackout window on R until step 9.

Before every step the role calls replication_restore_step with fresh reads of both clusters and runs only the step it returns, so a later run resumes where the records show. The module decides in this order, and the first that applies wins.

Refusals before step 1

The restore refuses a relationship, before step 1 and before any write, with a message that names its way on, when:

  • X is not both ESTABLISHED and read-only, an ENDED record lies at the target path beside X, or X has no recovery point;

  • the edge’s source directory holds a file;

  • the edge’s or the target’s qumulo_replication_address is missing or not an IP literal;

  • edge_rebuild_artifact_dir is empty, or the restore directory cannot be written;

  • the edge is in qumulo_edges, expects a license (qumulo_capacity.license other than none) and holds no active license;

  • the edge declares a qumulo_capacity.clamp that differs from the stored clamp, or the clamp plan fails;

  • the target path, or the edge’s source path, is, lies under or holds a portal spoke root;

  • the edge has a live relationship record whose source path is the same as or nested with this one’s, or whose target path on the edge overlaps it;

  • leftover records with R’s paths exist;

  • the check of the create on the target or of the authorize on the edge refuses.

Step 1’s refusals are per relationship, with outcome refused, on both entry points. replication_restore.yml (entry point playbook) also refuses the whole run, before any relationship, for a release in the run, an edge with no qumulo_previous_cluster_uuids, a name in qumulo_replication_restore that is not <target host>:<target path> or matches no present relationship, and nested source paths among the relationships to restore whose X exists. On the second pass (entry point second_pass), nested relationships are each refused, and a name that matches nothing fails the run in the report play.

Replication failover

The replication_failover role fails a declared relationship over to its target, copies the target’s writes back to the source, and fails it back. playbooks/replication_failover.yml runs it for the relationships of one source host, named in replication_failover_relationships, each <target host>:<target path>. The source and the target are the declared ones, whatever direction the records run in. Before each step the role reads both clusters with replication_info and replication_failover_plan names the relationship’s state and the steps its action has left. Fail over to a replica, and fail back has the task, and Replication says why the role works as it does.

Failover states

The plan names the state from the records. A is the source’s record, B the target’s. Each direction’s state is read from the record a verb moves first, so the other may lag. Two states, marked with an asterisk, read the same as another; the plan reads such records as the asterisked state unless the run’s last verb says otherwise.

A failback runs each relationship up to await_sync, waits for the waiting relationships, those on one target host together and the target hosts one after another, then runs each to the end. The role runs at most twelve rounds of read, plan and step for a relationship in one pass, and fails naming the next step when they run out; run it again to resume.

Failover refusals before the first write

The role reads and plans every named relationship before the first write of any, and a refusal of one stops the run. Troubleshooting lists the messages. The role refuses:

  • an empty replication_failover_relationships, a name that matches no present entry of the source host’s relationships, a target host outside the inventory, and a host without a qumulo_cluster_uuid;

  • a relationship with no record on the target, records in both directions or two in one, and a live target record from one of the source host’s qumulo_previous_cluster_uuids;

  • a relationship AWAITING_AUTHORIZATION or ENDED, and, for a resync or failback, a source record AWAITING_AUTHORIZATION or ENDED beside a target record that reads ESTABLISHED, and a state the action does not start from;

  • a resync or failback when the source did not answer (read once in the run, then every relationship is refused) or holds no record of the relationship;

  • a resync or failback of a relationship whose restore record is in <replication_failover_artifact_dir>/<source host>/restore/, which playbooks/replication_restore.yml finishes; a failover notes the record and goes on;

  • a make-writable on a target with no recovery point, and a failover for a job running on a source that answers, unless replication_failover_allow_partial_job lifts it;

  • a reverse toward an address that is not an IP literal, and a reverse into a tenant that has replication_enabled off (The replication address);

  • a real run with a step left and no replication_failover_allow_data_loss.

Failover outcomes

replication_failover_results holds one entry for each relationship: name, id, state_before, state_after, steps, the names of the steps run, plan, the lines of the steps the first plan listed, and notes. A check run reports steps empty and state_after equal to state_before. The playbook prints each as <name>: <state_before> to <state_after>, steps <steps>, then its notes.
