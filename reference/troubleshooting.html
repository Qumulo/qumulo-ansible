Connecting

On a host with qumulo_cluster_uuid, the first request is the identity guard’s, so the TLS, name and unreachable messages below start with identity guard: and end with ; no credentials were sent.

Message

Cause and fix

identity guard: https://...:8000 is cluster '...' (state ...), expected '...'; no credentials were sent

The address reaches another cluster than the inventory names, or a node that is not formed (UNCONFIGURED). Fix qumulo_api_host or qumulo_cluster_uuid.

identity guard: cannot read the node state of ... (...); no credentials were sent

The cluster answered GET /v1/node/state with an HTTP error, which the parentheses quote. Check the address and the port.

identity guard: unexpected node-state response from ...; no credentials were sent

The address answers, but it is not a Qumulo REST API. Check qumulo_api_host and the port.

identity guard disabled: expected_cluster_uuid is empty (a warning)

The host has no qumulo_cluster_uuid, so no task checks which cluster it reaches. Add the UUID.

https://...: TLS certificate verification failed (...); set ca_path to the cluster's CA, or validate_certs: false for a lab cluster

qumulo_ca_path does not name the CA that signed the cluster’s certificate. A newly formed edge serves a factory certificate nothing can verify (G-FACTORY-TLS); see Replace the factory certificate.

https://...: cannot resolve ... (...); check api_host

The name in qumulo_api_host does not resolve on the controller.

https://... unreachable for ...s: ...

The cluster did not answer within retry_timeout (default 300 seconds). Any request is resent after a refused connection. GETs, and writes whose route declares them safe to resend, are also resent after a dropped connection or HTTP 502, 503 or 504.

set exactly one of api_password or api_token for ...

The module has neither a password nor a token, or has both, and fails before any request. A password looked up from an unset environment variable is empty, and counts as none.

... failed: HTTP 401 ... (check api_username and api_password)

The login was refused. Check the password, or the vault entry it comes from.

... failed: HTTP 401 ... (api_token was rejected; access tokens are bound to one cluster and do not survive a rebuild)

The access token is for another cluster, or for an edge before its rebuild (G-TOKEN). Use a password, or a token issued by this cluster.

... failed: HTTP 403 ... (the API user lacks the RBAC privilege for this call)

The user lacks a privilege. The playbooks connect as admin.

... (redirected to ...; set api_host to the address that serves the REST API)

qumulo_api_host answers with a redirect. Give the address of the REST API itself.

... (this route does not exist on this Qumulo Core version)

The cluster runs a version that lacks a route the module needs. The collection is tested against 7.10.3 and later.

... runs Qumulo Core ..., older than 7.10.3, the oldest release qumulo.cluster is tested against (a warning)

The cluster runs a version below the collection’s tested floor.

A call to Nexus names nexus_api_token or nexus_api_url in place of the cluster’s options:

Message

Cause and fix

set nexus_api_token, or the QUMULO_NEXUS_API_TOKEN environment variable, to a Nexus user's API token

The task has no Nexus token. It fails before any request.

nexus_api_url must be an https URL such as ..., not ...; the token is never sent over plain HTTP

Give nexus_api_url as an https:// URL, or leave it unset for the default. It fails before any request.

Nexus ... failed: HTTP 502: ... (the gateway in front of Nexus, or Nexus itself, failed every try for ...s; retry_timeout sets how long to keep trying)

Nexus, or the gateway in front of it, answered 502, 503 or 504 to every try within retry_timeout (default 300 seconds). Nexus reads, retirements and join-key mints are retried until then; a mint retried this way may leave spare join keys in the Nexus organization, which nothing uses. Run the task again later.

Nexus ... failed: HTTP 401: ... (nexus_api_token was rejected; it may have expired or been revoked)

Issue a new token.

Nexus ... failed: HTTP 403: ... (nexus_api_token's Nexus role does not allow this call)

The token’s role lacks the permission the call needs.

https://...: TLS certificate verification failed (...); check nexus_api_url

The controller does not trust the certificate that nexus_api_url serves.

cannot resolve the host of ... (...); check nexus_api_url

The host of nexus_api_url does not resolve on the controller.

Nexus at ... unreachable for ...s: ...

Nexus did not answer within retry_timeout (default 300 seconds).

A change that may or may not have been applied

A write whose connection drops after the request was sent, or that a gateway answers with HTTP 502 or 504, may or may not have reached the cluster. The collection never resends such a write. It reads the cluster back instead (Maybe applied gives the reasons):

  • When the read shows the change took effect, the task succeeds, and its notes say write reconciled after a lost connection.

  • When it cannot tell, the task fails with changed: true and maybe_applied: true in its result, and a message that starts with the request and ends with the reason. The last row is the one failure that has changed: true alone:

Message

Meaning

PUT ...: the connection was lost after the request was sent; the change may or may not have been applied

The connection dropped and the read back failed or was not possible.

...: HTTP 502 from a gateway; the change may or may not have been applied

A proxy or load balancer answered, perhaps after forwarding the request. The same message with HTTP 504 exists.

...; reading back did not confirm it: ...

The read back shows the object not yet as declared.

...; ... cannot be read back, so whether the change took effect is unknown

The change was to a field the cluster never returns, such as a password.

...; reading back shows the clamp is ..., not the requested ... bytes; it was not sent again

A clamp write was lost. A clamp write re-forms quorum, so the module waited for the cluster before reading.

...; the registration status is ...; a join key is single-use, so set join_key to a new key, or nexus_api_token to mint one

A Nexus registration was lost, and the key it used is spent (G-NEXUS-KEY).

...; this delete was for recreate, so the create was not attempted

A recreate’s delete was lost; the object may be gone and was not created again.

...; the comparison's snapshot of <path> may exist, and expires by itself a day after it was taken. Nothing was sent to ...; run again to compare and reconnect

A replication_reverse reconnect lost the answer to the snapshot it takes to compare the directory with the recovery point. The result has changed: true and no maybe_applied, since no verb was sent. Run the task again.

In every case, run the task again. It reads first and writes only what still differs. Forming an edge is the one write that says so itself: the connection was lost as the create was sent, so the node may never have received it, and running the task again is safe.

... failed: HTTP 412 ... (the resource changed between read and write; re-run the task) means another writer changed the object between the module’s read and its write, and the module’s retries ran out. Run the task again.

Refusals that wait for a release

A replication relationship that another record holds is refused with the holder’s id:

... cannot be authorized: relationship ... from ...:... holds ... (ESTABLISHED); a release bound to ... naming O2
deletes it, and the directory keeps its data

Every unmet row of the overwrite table is in the result’s unmet, and the releases that would lift them are in releases. A release, <target host>:<target path>@<record id>:<rows>, lifts only the rows it names, and only while the record with that id exists. It is passed with -e for one run, never in the inventory. Some rows no release lifts: a live relationship at a path that contains the target path or lies inside it, one replicating back to the source, and a live record of the relationship that the source does not hold. ansible-doc qumulo.cluster.replication_target describes every row. Replicate a directory shows the procedure.

A relationship from a rebuilt source is held, not refused, while its replica may be the only copy of the source’s data: <target host>:<target path> is held: .... When the holder allows it, the message names the restore, the source edge’s second pass or playbooks/replication_restore.yml, and prints the release only for keeping the replica as plain data; otherwise it names the copy back and the release. The restore’s records and steps are in Replication restore.

The inventory and the cluster disagree

Message

Cause and fix

Validation of arguments failed: followed by <variable>[.<path>].<key>. Supported parameters include: <keys>.

A variable of the baseline holds a key that it does not take, such as qumulo_smb_settings.sesion_encryption for session_encryption, a connection option such as request_timeout in an entry of qumulo_smb_shares, which the play’s module_defaults set, or tenant, state or declared_access_key_ids, which the role sets itself. Ansible stops the role before its first task, so the role wrote nothing. The message names the dotted path to the key and lists the keys taken where the key sits; with keys in more than one place, the list is for one of them. It does not say which entry of a list holds the key, so search the inventory for the key. Correct it or remove it. qumulo_network.managed_interfaces, qumulo_s3_bucket_policies[].policy and qumulo_capacity.license_document take any key, so a misspelling in them is not caught here; step 2 refuses qumulo_tenants[].identity. A tenant’s smb_settings and nfs_settings are checked at step 2 instead (The inventory’s tenants). A rebuild gives the same message before it drains the edge (Rebuilds).

...: ... belong to Terraform by qumulo_terraform_owned_areas; remove the variables or keys named, or the areas from that list

A declared variable, or a key of one such as qumulo_authoritative_dns.fqdn for dns.fqdn, is in an area Terraform owns. Remove the key or variable named, or the area from the list (Declare the areas the root owns). When audit, dns.fqdn or network.floating_ips is among the areas, the message adds ; or, for <areas>, set qumulo_take_over_from_terraform: true, which hands audit, dns.fqdn and the floating addresses back to this role together.

The inventory gives no qumulo_terraform_owned_areas, the cluster was formed by the Terraform provider and its qumulo_cluster_kind is cnq or unset, and a variable or key in the area network.floating_ips is declared, such as floating_ip_ranges in a tenant’s networks. With the kind unset, <kind remedy> is ; or, on an edge or other on-premises cluster, set qumulo_cluster_kind: edge or baremetal, which leaves the floating addresses to this role; with cnq it is left out. Remove the variable or key named, or take the floating addresses over from Terraform. On an edge or bare-metal cluster, declare its qumulo_cluster_kind instead.

...: <places> declare floating addresses, which belong to Terraform by <owner>; remove them<remedy>, or set qumulo_take_over_from_terraform: true, which hands audit, dns.fqdn and the floating addresses back to this role together

floating_ip_ranges in qumulo_network.frontend_networks[<index>] is declared, and Terraform owns the floating addresses. <owner> is qumulo_terraform_owned_areas when the inventory gives the list, which then names network.floating_ips, and qumulo_managed_by: terraform_provider, since the provider applies its own floating addresses when it does not and the cluster’s qumulo_cluster_kind is cnq or unset. A tenant’s floating ranges are refused by the area row above. Remove the ranges, or, with a list, network.floating_ips from it, which <remedy> says as , or network.floating_ips from qumulo_terraform_owned_areas, or take the floating addresses over. With no list and the kind unset, <remedy> is , or, on an edge or other on-premises cluster, set qumulo_cluster_kind: edge or baremetal, which leaves the floating addresses to this role, and on an edge or bare-metal cluster declaring the kind is the fix; with cnq it is left out.

...: qumulo_terraform_owned_areas must list network.floating_ips for a cnq cluster with qumulo_managed_by: terraform_provider, which re-applies them; add network.floating_ips to it, or set qumulo_managed_by: none

The host’s qumulo_cluster_kind is cnq, its qumulo_managed_by is terraform_provider, and its qumulo_terraform_owned_areas leaves out network.floating_ips. The Terraform inventory plugin refuses the same output entry. Add the area to the list, or set qumulo_managed_by: none when the provider did not form the cluster.

...: qumulo_audit_destinations declares the CloudWatch destinations ..., which belong to Terraform by qumulo_terraform_owned_areas through audit.cloudwatch; remove them, or set qumulo_take_over_from_terraform: true, which also hands the floating addresses back to this role

The inventory declares CloudWatch audit destinations in an area Terraform owns. Remove them, or take the area over from Terraform.

...: ...: the cluster refuses quotas and snapshot policies under a portal's spoke root (G-SPOKE-PATHS), and an S3 bucket there would serve the hub's data; declare them on local directories, or on the hub

trustee '...': ... api_identity_unsupported_domain_error: Unknown SID domain ...

The node has not found a name in that SID’s domain since it started, so it refuses the SID, joined to a domain or not (QUIRK-100). The message names a trustee you declared; an entry the cluster reads back never causes it in file_acl, smb_share or directory. S-1-5-11, the SID of Authenticated Users, cannot cause it, because the collection looks it up by its name (why). For another SID, find a name in its domain first, such as ad:<NETBIOS>\Domain Users, in an identity_info find_trustees task before the failing one, then run again (Look up identities, DNS names and paths).

trustee '...': the internal domain holds only File Owner and File Group Owner

An internal: trustee names something else. The cluster’s internal domain holds only those two names, which the collection takes in any letter case. Write internal:File Owner or internal:File Group Owner, or another form for the identity you meant (Trustees).

...identity {...} cannot be written as a trustee: it has no SID, uid or gid, and no name the trustee grammar holds

The cluster returned an identity that capture_info, filesystem_info or s3_info reads back, in an ACL, a directory’s owner or group, share permissions, a bucket policy or an access key’s owner, and the grammar has no form for it. Open an issue on the collection’s public repository, Qumulo/qumulo-ansible, with the identity from the message, and meanwhile manage it outside the collection. file_acl, smb_share and directory report such an entry by its name and can replace it, but cannot keep it, because no declaration names it.

...: local group '...' does not exist; create it with qumulo.cluster.local_group first

Declare the group in qumulo_local_groups; the baseline creates groups before users.

the cluster is joined to ..., not ...; leave it first with ad_domain state=absent

The cluster is in another domain. See Rejoin Active Directory.

... is set only by a join: the cluster has '...', not '...'; leave with ad_domain state=absent, then join again

ou or domain_netbios changed. Leave and join again, as above.

cannot rename '...' to '...' while it is joined to ...: the name is its computer account; ...

Leave the domain, rename, then join again.

joining ... needs join_user and join_password

Give both in qumulo_ad.

the cluster is joined to ..., and a joined cluster takes no keytab: its Kerberos keys are its computer account's (G-KRB-AD); leave with ad_domain state=absent first, or declare no keytab

kerberos_keytab would install or replace a keytab on a cluster that is in a domain, or joining or leaving one, in check mode too. Leave the domain, or declare no keytab (G-KRB-AD; Join a cluster to Active Directory).

qumulo_kerberos declares a keytab to install and qumulo_ad a domain to join, and the cluster takes no keytab while joined (G-KRB-AD); ...

The baseline’s opening check found a keytab to install and qumulo_ad in one inventory, and made no write. Remove the keytab, or set qumulo_kerberos.keytab_state to absent.

ad_domain_standalone_kdc_error (HTTP 409), from the join

The cluster holds a keytab, and refuses a join while it does. Delete the keytab, with keytab_state: absent or kerberos_keytab with state: absent, then join (G-KRB-AD).

keytab_path ... is encrypted with Ansible Vault; a module reads the file as it is and cannot decrypt it; encrypt the keytab's base64 instead and give it as keytab: "{{ lookup('ansible.builtin.file', 'FILE') }}", which decrypts it

keytab_path names a vaulted file, and the module fails before any request. Use the recipe in Encrypt a binary secret such as a keytab.

Networks ... each carry an IPv4 default gateway, but a cluster on chassis nodes takes one IPv4 default gateway, and the module refuses a second on every cluster. Keep the gateway on one network and set default_gateway: "" on the others; a new network left without default_gateway has none.

Two or more STATIC networks carry a default gateway of one IP version (the message says IPv6 for a gateway written with colons). The baseline refuses it at step 2, before any write, step 3a’s tenant writes included, and network_config on its own refuses it before its write, on every cluster and in check mode too. Keep the gateway on one network and set default_gateway: "" on the others. When the cluster already gives each of those networks a gateway of that version, the module warns and goes on.

Tenants

Qumulo marks the multitenancy REST API as preview in Qumulo Core 7.10.3 and 7.11.0. The collection manages tenants through it on those releases, and a later Qumulo Core release may change it.

The baseline makes these refusals at step 2, before any write, and the modules tenant and network_config make the continuity ones for a write run alone. <variable> is qumulo_management_network in the role and management_network in a module, and <port variable> is qumulo_cluster_port or cluster_port. A module run alone words messages 1 to 4 for its own options. Manage tenants has the procedures, and Tenants and the continuity rule the reasons.

A refusal of the plan fails with msg, which holds each refusal’s message on a line, and refusals, each message with the names it gives, such as tenants, networks, entries and the play’s api_host. The plan behind the refusal appears only at verbosity 3 or more (-vvv), under plan. At -v or more Ansible prints each task’s result, and the role’s network read at step 2 returns the network document, so a log kept at -v or more holds every address range of the cluster, with or without plan.

The play’s connection

The continuity rule judges a tenant create, a change of rest_api_enabled or web_ui_enabled, a tenant delete and a network write. Each message below is the first that applies, in this order.

Message

Cause and fix

The cluster's networking is host-managed and it has no frontend network yet, so with a second tenant REST would listen on no network. List its HOST network under one tenant in qumulo_tenants and run once before adding the second tenant, ...

Message 1. The cluster has no frontend network to carry REST. Declare its HOST network under the one tenant and run the baseline once, then add the second tenant (On networking the host manages). The message ends with what to do when the cluster’s network status is unavailable: set qumulo_management_network to that network’s id.

This run removes network ..., which carries this play's connection. List it under the networks of a tenant in qumulo_tenants that is not state: absent, or set qumulo_allow_management_disruption: true and qumulo_api_host_after to the address the play uses after the run.

Message 2. The network document would drop a network that carries qumulo_api_host. Keep the network under a present tenant, or consent and name the address to use afterwards.
