The upgrade: variables, steps and files

Lookup tables for the upgrade playbook, ansible-playbook qumulo.cluster.upgrade: its inventory variables, the variables for one run, the role variables, the images list, the steps of a run and of a hop, the report and the other files a run writes, and the sources the upgrade supports. To run an upgrade, see Upgrade a fleet. To recover from a stopped one, see Recover an upgrade that stopped. For the reasons behind the hop rules, the ordering and the records, see How upgrades work. Troubleshooting quotes every refusal (F1 to F34) and warning (W1 to W12).

The images list

qumulo_upgrade_images holds entries of two forms.

Form

Gives

A URL or an absolute path whose file name is qumulo_core_<version>.qimg (on-premises) or cloud_qumulo_core_<version>.qimg (cloud)

The image. The plan reads the release and the kind from the file name. A URL is http:// or https://. Anything else, such as a relative path or another URL scheme, is refused (F2).

A mapping {version, image, kind, build}, for an image under another name

See below.

Mapping key

Required

Value

version

yes

The release the image holds, as a quoted string such as "7.10.0.3". A number is refused.

image

yes

A URL or an absolute path.

kind

yes

on-prem or cloud.

build

no

The build the cluster must end on, for the entry’s own release. Only a mapping entry can declare one. A host whose target is that release and that already runs it on another build is refused (F4). A commit that ends on another build fails, after the commit, which cannot be undone.

Rules the plan applies to the list:

  • The whole list ascends by release. An on-premises and a cloud entry of one release may sit in either order, but a list that groups all of one kind before the other is out of order. The plan refuses a list out of order rather than sorting it (F4).

  • No release appears twice for one kind (F4).

  • A URL’s query string and user information are passed to the module apart from the rest of the URL. The plan, the report and every message hold the URL without them. A path and a plain URL are printed in full.

  • An image file name that names no release, and an entry that is not a string or a mapping, are refused before F4.

From the entries of its kind above its running release and at or below its target, the plan picks each hop as the furthest entry the quarterly rule accepts:

  • A hop out of quarter x.y lands on x.(y+1).0 or one of its dot releases, x.(y+1).0.w, never on a later patch of that quarter. The next quarter is x.(y+1) by arithmetic, whatever the list names.

  • A hop inside a quarter lands on a later release of that quarter.

  • No hop before the last is a letter release.

  • The last hop is the host’s target.

A run

ansible-playbook qumulo.cluster.upgrade -i <inventory> runs these on qumulo_clusters, in order:

  1. Reads. Each cluster’s cluster_info with the subsets node, version, license, product, upgrade and portals: UUID, release and build, license, product, portals, and the upgrade’s status, preflight, reboot status and protection. A cluster whose read fails leaves the play, and the plan treats it as outside the run.

  2. The artifact directory. A host whose edge_rebuild_artifact_dir or cluster_upgrade_artifact_dir is empty, as a host given with -i as a list is, fails.

  3. The commit records. The record of every inventory host, if it has one, is read from its cluster_upgrade_artifact_dir.

  4. The plan. upgrade_plan, once, from every inventory host and not only the play’s: their reads, qumulo_upgrade_* variables, qumulo_portal.hub, qumulo_replication_relationships and commit records. Every refusal fails the run here, together, before anything is written. Every warning is printed. A --limit run plans its own hosts, and a limit that leaves out part of a portal component is refused (F13).

  5. The locks. Each host in the plan’s lock_hosts takes its restore lock (Restore locks). Then the commit records the plan decided can go are removed: a record is removed only on a host still in the play, and only while its file still has the digest the plan read.

  6. The hops, by the cluster_upgrade role, one after another, each on every host at once.

  7. The end. Each lock is released however the hops ended. A run that stopped before its last hop then fails, naming the hop and the reason, and exits non-zero.

The nine steps of a hop

Step

Runs on

What happens

A host that fails

1

The hosts the hop moves and does not hold

Waits out a reboot still under way from an earlier hop or run, then waits for the upgrade’s preflight to clear, up to cluster_upgrade_unblock_timeout.

Leaves the play; its unit is held.

2

The same

Every host prepares at once: verify, then the prepare, which installs the image beside the running build.

Stays in the play for step 3’s second prepare, unless no second prepare can lift the refusal.

3

The hosts whose first prepare failed, then every host of step 2

A host whose first prepare failed prepares once more. Then the upgrade module checks that each host may commit: the preflight, the image’s release, and the tolerance its reboot needs.

Leaves the play; its unit is held.

4

Once, when a host of the hop declares a window

The hop’s commits may begin only inside the maintenance window (The maintenance window).

Outside the window, every unit is held except the moving members of a split component the hop closes.

5

Each commit step’s hosts that are ready and not held

The commits, step by step of the plan’s schedule. Each host’s readiness is checked again just before its own commit.

Leaves the play; its unit and every unit that follows it are held.

6

Each moved component’s hub, or its spokes when the hub is outside the play; the sources of the replication relationships that touch a moved host

Each moved portal component’s portals are read until ACTIVE, up to cluster_upgrade_peer_timeout. Each replication relationship that touches a moved host is read once, with no wait.

Never fails. A portal timeout, a read that fails, a relationship the source does not list, and a last job’s error are each a report line.

7

The hosts that committed, and those the plan only reboots

Waits for a platform upgrade’s reboots, up to cluster_upgrade_reboot_timeout.

Leaves the play.

8

As step 6

Reads the portals and relationships again.

Never fails.

9

Once, also when the hop fails

Writes the report.

Step 6 does not wait on a component the hop left on two releases, on a component that stays split without closing, or on one whose members took a rolling platform reboot; each gets a report line instead. A plan with no hop, as when every cluster is at its target, runs none of this, and the report holds the plan alone.

At each hop’s start, outside check mode, each host of upgrade_lock_hosts renews its restore lock to the hop’s lease. A renewal that fails stops the run before the hop.

A check run

Part

In a check run

Reads

Sent.

The plan

Made in full, with every refusal and warning.

Restore locks

Judged, not written. A refusal is reported as a prediction with the hosts the run would hold, and a takeover is reported as one.

Commit records

Reported as the records the run would retire or drop, not removed.

First hop

Reboots

Verify reads whether a hop is a software-only upgrade or a platform upgrade, SOFTWARE_AND_PLATFORM, which also reboots every host. The report gives each host’s upgrade_type. A hop’s type depends on its source, so one release can be either.

Setting

Effect

qumulo_upgrade_reboot unset or rolling

The hosts reboot in groups, each once the cluster has reprotected after the last.

qumulo_upgrade_reboot: all

Every host reboots together, one longer outage. On a platform upgrade, Qumulo Core reboots only once the cluster has reprotected fully with every node armed, so the readiness checks first wait for the current node fault tolerance to equal the configured one, up to cluster_upgrade_wait_timeout (F23).

qumulo_upgrade_reboot_set_size unset

Qumulo Core sizes each group at the current node fault tolerance minus one, at least one.

qumulo_upgrade_reboot_set_size above the configured node fault tolerance

Refused before anything is sent (F20).

qumulo_upgrade_reboot_set_size above the current node fault tolerance

Waited for before the prepare and at each readiness check, up to cluster_upgrade_wait_timeout (F7). Qumulo Core checks the count once more after every node is armed, and a drop in the tolerance after the last check leaves every node armed and nothing restarted (G-UPGRADE-COUNT, in Gaps).

qumulo_upgrade_reboot_set_size below 1

Refused.

qumulo_upgrade_reboot_set_size with qumulo_upgrade_reboot: all

Ignored, with a warning (W10).

Configured node fault tolerance 0, as on an unprotected edge or a Cloud Native Qumulo cluster of fewer than three nodes

Every host reboots at once whatever qumulo_upgrade_reboot says, with a warning where a declaration is ignored (W10).

qumulo_upgrade_reboot: aggressive in the inventory, or qumulo_upgrade_aggressive=true

Refused (F11).

A reboot that was paused outside the run fails at once, at step 1 or step 7 (F25). One that stopped on an error fails at once (F26). One that outlasts cluster_upgrade_reboot_timeout fails (F24).

The maintenance window

qumulo_upgrade_maintenance_windows is a list of ranges. A host that declares none may commit at any time.

Range key

Type

Value

start_hour, end_hour

integer

0 to 23.

start_minute, end_minute

integer

0 to 59.

on_days

a string or a list of strings

MON, TUE, WED, THU, FRI, SAT, SUN, or EVERY_DAY. Names are not case-sensitive.

A range whose end is at or before its start runs past midnight, and on_days names the day it starts. A value outside these limits, a name that is not an IANA timezone, and ranges without a timezone are refused (F34).

Case

What the run does

Whether a hop may commit

Checked once per hop, at step 4, before its first commit, against every host the hop moves that declares a window and is not held. The hop is inside only when every such host is inside one of its own ranges.

Inside the window

The hop commits all its rounds, the later ones past the window’s end if the hop runs long.

Outside the window

Nothing is committed. The hosts stay prepared, the report gives when the window next opens, and the run ends after the hop with F9 and a non-zero exit.

Prepares

Run whenever the playbook runs, so a run started before the window stages the images and then stops with F9. A prepared upgrade is lost at any quorum change, and a presigned URL differs at the next run, so the run inside the window may prepare again.

A rerun outside the window

Commits only what closes a split: the moving members of a portal component whose members run two releases at the hop’s start, when the hop brings every member to one release and the component follows no held unit. Each gets a report line. F9 holds everything else.

Hosts whose windows share no time

A warning (W11).

Connections

Setting

Effect

Request timeout of verify and prepare

upgrade sends each with a request timeout of its own, 2700 seconds on a source of 7.10.3 or later and 4500 seconds below. The address the playbook connects to must hold an idle connection that long.

qumulo_upgrade_api_host

The address the playbook connects to in place of qumulo_api_host. A multi-AZ Cloud Native Qumulo cluster’s qumulo_api_host is a network load balancer that closes a connection idle for 350 seconds by default; a node’s address avoids that.

forks

Each prepare holds one fork while it waits. A hop of more clusters than forks, or a commit step of more hosts, runs in batches. The run warns when forks, or cluster_upgrade_prepare_throttle when lower, is below the hop’s size or its largest commit step (W6). Set with -f or in ansible.cfg.

A limited release

A letter release, such as 7.10.3A, is refused as an upgrade source unless the rule is waived (F1). qumulo_upgrade_allow_limited_release: true sends Qumulo Core’s waiver on that host’s first hop, with verify and the prepare.

Source release

Waiver sent

What it lifts

Requires

7.11.0 or later

compatibility_overrides=allow_upgrade_from_limited_release

The limited-release rule alone.

Nothing more.

Below 7.11.0

override_compatibility_check=true

Every compatibility rule Qumulo Core checks: a prohibited release, a limited release, a developer source, a source off a release branch, a downgrade, the upgrade window, a developer target build, a build not later than the running one, and the license check.

The first hop declares the exact build in a mapping entry (F16). The module verifies with the waiver first and prepares only when verify reads the declared release. Once the cluster runs the new build, another build fails at once.

A mapping entry’s build applies to every host whose hop lands on that entry. For a build for one limited-release host, see Upgrade from a limited release. A letter release is never an intermediate hop, and may be a host’s final target.

A check run’s prediction.

A component’s window is {started, ended, seconds, open, uncommitted}, from its first member’s commit start to its last member’s commit done, or null when no member’s commit started. A peer reading of a portal is {component, host, active, seconds, line}, with active null when the step skipped the component. A reading of a replication relationship is {source, target, error, line}.

The plan

The plan, in plan of the playbook’s upgrade_plan result and of the report:

Key

Holds

hops

The hops in order. Each has number, release, lease, moves, components, steps, units, hosts, windows, notes and forks_warning. A host’s entry gives its image_index, image_redacted, version, build, kind, reboot, unit, round, wave, step, the hosts a failure of it holds, and reboots_only for a host on the target build still rebooting.

lock_hosts

Each host the run locks, with the hosts its lock protects: itself and its replication targets.

records

The commit records to retire and to drop, each {host, path, digest, line}.

skipped

The hosts already at their target.

refusals

Each {host, code, message}.

warnings

Each {code, host, message}.

notes

Each {host, message}.

A hop’s lease, in seconds, bounds how long the hop can take. The plan computes it from the four timeouts, the prepare’s request timeout (Connections), forks and the throttle, and each restore lock is renewed to it at the hop’s start. forks_warning is W6’s text, or null, and is printed by the role.

Restore locks

The lock is the one a replication restore takes, with the holder upgrade.

Property

Value

Path

<restore-artifacts>/<host>/restore/lock

Taken on

Each host the plan moves or reboots, and each host in the play whose declared replication targets one of them.

Taken

Once, after the plan, with a lease of the first hop’s lease.

Renewed

At the start of each hop, outside check mode, to that hop’s lease.

Released

At every end the run itself reaches: hops done, a hop that failed or stopped, a lost lock, or a host that failed after its take.

A lock another run holds

Fails that host with the lock’s own message (F22). The host and every host it replicates to are held in every hop that moves them, and the run ends after the first hop that moves one of them. A check run reports it as a prediction.

A source outside the run

Cannot be locked by the run. The plan warns that a restore of it started meanwhile is not held off (W9).

This controller (same host name, boot ID and PID namespace)

Another controller, or one without /proc

Its lease has run out.

For a hop the lease is many hours. Troubleshooting quotes the lock’s warnings and refusals.

Before the plan, the playbook runs replication_restore_info once for each distinct edge_rebuild_artifact_dir of the qumulo_clusters hosts, as the edge_rebuild role computes it, artifacts beside the host’s inventory source by default, and passes the records and locks it finds to upgrade_plan as restore_files. It scans in check mode too, since it only reads. The plan warns W1 for a host it moves or reboots, once for each record or lock that names the host:

Found

Names

A restore record

Its edge, the target_host of its key, and every target of the edge’s present replication relationships.

A live restore lock

Its host, and every target of that host’s present replication relationships.

A lock on a host the run locks itself is left to the lock step (F22). A lock that is gone or expired, and a file the scan cannot read, are not W1: the next restore or upgrade of the host takes a lock over with a warning, and a restore that reads an unreadable file stops on it, naming it, and so does this run’s lock step on an unreadable lock of a host it locks. Troubleshooting quotes W1, and Find and clear restore records and locks reads the scan’s result.

An open restore record is a file named by 64 hexadecimal digits and .yml in <restore-artifacts>/<host>/restore/. A file named done- followed by the digits is a finished restore’s stamp.
