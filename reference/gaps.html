G-LICENSE

License after a rebuild

Licensing an edge after a rebuild

A license is bound to the cluster UUID, and only Nexus issues one, for a UUID it sees once the cluster is registered. A customer organization’s users, its administrators included, can neither create nor see licenses in Nexus, which answers them 403. The cluster takes a license document through the API only at /v1/debug/license/validate and /v1/debug/license/activate, which need PRIVILEGE_DEBUG; a document applied there is active at once. How Qumulo delivers a license document to a customer is not yet defined.

The collection never creates a license, never reads one from Nexus, and never waits for one. The operator gives the document Qumulo issued for the UUID to the collection in qumulo_capacity.license_document; qumulo.cluster.license applies it through the debug routes, unless the cluster holds it already (by its key), and otherwise reports the license and the UUID one must be issued for. A new UUID takes two passes: the first baseline hands the license off and leaves the clamp for the license, and the second, the baseline again or edge_license_complete.yml, which run the same step, applies the document, or finds the license the cluster holds, and then sets the clamp. An edge that declares qumulo_capacity.license: none runs without a license: nothing is handed off, and its clamp is written with no license, by the first pass and the second. A raised cap applies at the next quorum formation, which qumulo.cluster.license reports as needs_quorum_bounce in the run that applied the document, and as cap_waits_for_formation in a later run while the file system is still the size an edge formed without a license has. The integration lane mints a test license that expires a day later with raw Nexus calls and a token whose user may create licenses

A release route on the cluster that installs a license document

open

capture_info, clone_host_vars, edge_cache_route, license

G-NET-APPLY

Network apply status

Verifying that a network change has applied

GET /v3/network/status answers HTTP 500 on the Qumulo Core container. The VM edge, a package install on a virtual machine whose network its host manages, answers it; host-managed CNQ has not been observed.

network_config verifies the stored document, on every cluster. The continuity rule reads a 500 from the status as unavailable. With two or more tenants after a judged write, a declared management network (management_network) is trusted without the check that a HOST network shows on a device, and an undeclared one is refused with a message that names the option when an address of api_host is on no network’s ranges or on a HOST network; an address that the ranges place on a STATIC or DHCP network needs no status, and the write is judged as usual. network_config reads the status only for such a write, and never with one tenant. network_info lists its status and api_host_network subsets in unavailable_subsets with the reason, from one read of the status, and gathers the other subsets. tenancy_plan takes the status, or the reason it is unavailable, as options, and judges the run’s writes on it as tenant and network_config do: with the status unavailable it trusts a declared management network and refuses an undeclared one that needs the status

G-TENANT-BACKEND

Backend networks in a tenant

G-TOKEN

Access tokens

Creating access tokens

The secret is shown once, a user can hold two tokens and expired ones count, and every token is dead after a rebuild.

access_token keys a token by its user, since the cluster takes no name for one. present makes a token when the user holds none, and otherwise sets enabled and expiration_time on each token the user holds. rotated always changes: it makes a new token, writes its bearer to a file, confirms the token in a listing, and then deletes the old ones, and it is refused before any write for a user who holds two tokens, expired ones counted. The bearer goes to the result once and at once to a file of its own, readable only by its owner, in secret_destination; a task without no_log or the destination is refused before any write. A rotation whose later step fails can leave the user with two tokens, and no option of the module deletes only the old one; the failure names the old token’s id, which qq auth_delete_access_token or DELETE /v1/auth/access-tokens/{id} deletes outside the collection, and a user refused at two tokens is told the same. A create whose connection is lost is not sent again: the module lists the user’s tokens and deletes any it did not hold before, whose bearer is lost, and with them any token another client made in the same moment; when that listing fails too, the task fails with maybe_applied, saying a token whose bearer is lost may be left and how to replace it. The rebuild preflight counts the tokens a cluster holds.

Do not count expired tokens; name tokens

open

access_token, edge_rebuild_preflight

G-S3-KEY

S3 access keys

Creating S3 access keys

The cluster makes both the key’s id and its secret, returns the secret only in its response to the request that makes the key, and holds at most two keys per user; no route imports a known key, so a rebuilt cluster has none of the old keys.

s3_access_key keeps a key by its id, or makes sure the user holds one, and makes a key only when none meets the declaration, and for a declared id only while the user holds fewer keys than the inventory declares for it, so a rebuild restores each declared key. It writes the new secret at once to a file of its own, readable only by its owner, in secret_destination, returns it in that run only, and refuses to make a key without no_log or a destination. The baseline makes keys last, writing the secrets under the host’s artifact directory; the rebuild preflight counts the keys a cluster holds. Not handled yet: an entry without an id declares no key, so a user with such an entry beside entries with ids is not restored by a rebuild, and which key the id-less entry keeps depends on the order of the entries; a user’s entries are matched by how they spell the user, so local:svc and LOCAL:svc count as two users; and check mode does not look at secret_destination, so a file there passes check mode and fails the real run before any key is made

An import route for a known key, or a description on each key to find it by

G-REPL-PEER

Replication after a peer rebuild

Keeping a replication relationship across a peer rebuild

Relationship ids are generated, a relationship pinned to the old peer certificate never reaches ENDED, and the delete notification is sent only once.

The target cluster’s UUID is part of the source’s key, and the address a setting. A changed peer is found at the declared address, or by a previous UUID of the target host at any address, and is recreated create-first once the target check has passed: the new relationship’s target UUID is read back before the old record is deleted. While the role defers a relationship into an edge, a delete-only pass removes previous-UUID records at the declared address or with the secure-connection error. A rebuilt source’s stale target record is held until a copy back and a release. An edge that is a target is recreated only in its second pass. The rebuild preflight reads each peer’s record of a declared relationship, matches a peer by its current or a previous UUID, and fails fast on a relationship the inventory does not declare, or on a declared source whose record is ENDED or pending

A peer-UUID-mismatch state

open

G-REPL-ONESHOT

One-shot replication operations

Creating and authorizing a replication relationship, and a make-writable, reverse or reconnect by relationship id

Create and authorize are one-shot, and so are replication_reverse’s verbs. A repeated create makes a second relationship, and a create that fails halfway leaves a pending record on the target. A repeated authorize fails. A create to an address that reaches another cluster leaves an ENDED record there after the source’s delete.

Match by key before any create, and reconcile a lost create or authorize by listing, never by sending again. The target prunes stale pending records of the key, and a misdirected create is deleted at once. Pending records stay on both sides when a declaration is abandoned before its authorize. replication_reverse sends each verb only from the state it starts from, the make-writable from ESTABLISHED with a recovery point and the reverse and reconnect from DISCONNECTED, and reconciles a lost answer by reading the record. A restore abandoned before its make-writable leaves its relationship on both sides until its abandon exit deletes it

G-REPL-IDMAP

File ownership through replication

Replication carries a file’s owner and group as NFS ids when they are local users and groups other than the built-in ones.
