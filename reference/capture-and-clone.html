What capture and clone read and write

Capture reads a running cluster and writes the inventory variables that declare it. A clone derives those variables for a second, fresh cluster from the first cluster’s capture. This page lists the variables each writes, what each leaves out, the secrets each names instead of reading, and the shape of the files.

The tasks are in Adopt a cluster you already run and Clone an edge’s configuration onto a new edge. The reasons are in State management and Rebuilds.

Every captured variable the host does not already have, with the same trailing comments.

  • qumulo_capture_dir defaults to a captures directory beside the inventory source that defines the host: in the source’s parent when the source is a directory, in the file’s directory when it is a file. When several sources define the host, the first in sorted order is used. A host that comes from no inventory file or directory needs qumulo_capture_dir.

  • The default capture directory is never inside a directory given to -i in that run, because Ansible reads every .yml and .json file in an inventory directory as inventory. With a file source such as -i inventory/hosts.yml the default is inventory/captures/, which a later run with -i inventory reads as inventory; set qumulo_capture_dir in that layout.

  • The host file is written once and never rewritten: the write uses force: false, and a host that already has host_vars fails first (see Adoption refusals).

  • The capture file holds qumulo_cluster_uuid. The host file does not when the inventory defines it, as hosts.yml does.

  • Capture uses the connection variables (qumulo_api_host, qumulo_api_password and the rest) to reach the cluster and never writes them, so no file holds one.

  • When the host defines qumulo_cluster_uuid, the capture fails on a cluster with another UUID (the identity guard).

Adoption refusals

A node that belongs to no cluster (state UNCONFIGURED) has nothing to capture, and the playbook fails for it with or without qumulo_adopt. With qumulo_adopt=true the playbook also fails for a host when:

  • host_vars/<host>.yml, .yaml or .json, or a host_vars/<host>/ directory, exists beside any -i source. The capture file is still written.

  • the host is in more than one -i source, so there is no single host_vars directory to write.

  • the host is in no -i source, even with qumulo_capture_dir set: the message is “no inventory file or directory defines it”.

  • the host_vars file would hold a network the inventory also declares, or a share or export the inventory declares with other values, or the inventory defines qumulo_tenants and contradicts a captured tenant. The host_vars file is not written; the capture file still is. See Declared again by the inventory.

Troubleshooting: adoption quotes the messages.

Declared again by the inventory

The baseline refuses an SMB share, NFS export or network that two entries declare. A variable the file holds outranks the inventory’s, so the inventory’s qumulo_tenants, qumulo_smb_shares, qumulo_nfs_exports, qumulo_factory_defaults and qumulo_network count only where the file leaves them out, and each stays in force beside the file’s variables. The adoption and the clone compare the file’s entries with the inventory’s before they write the file. The host_vars_duplicates filter decides each case.

What counts as the same entry:

  • An SMB share is the same one when its share_name is the same ignoring case, and an NFS export when its export_path is the same, each within one tenant. A network is the same one when its id is the same, whichever tenant holds it. A network under a tenant declared absent is not counted.

  • A flat entry claims the tenants it names in tenants, every declared tenant for tenants: all, and, when it names none, the only present tenant. With tenant_id: 1 it claims tenant 1.

  • Tenant 1 is the present entry renamed from Default, else the present entry named Default. The cluster has none when the capture notes it has no tenant 1, as it does when it declares Default with state: absent. Then tenant_id: 1 and a factory removal claim no tenant.

  • With qumulo_tenants unset or [], the cluster’s one tenant is what a flat entry with no tenants, tenant_id: 1 and a factory removal claim.

  • A qumulo_factory_defaults that sets smb_files_share or nfs_root_export to absent claims tenant 1’s factory Files share or / export.

An entry of the file is left out, with a comment at the end of the file that names the inventory’s entry, when the inventory:

  • declares the same share or export with the same values. The entries are compared in the spelling the modules compare them in (what is compared). For other values, only the keys the inventory’s entry gives are compared. What the file’s entry gives beyond them depends on who creates the share (a key the inventory’s entry leaves out).

  • removes the share or export, with state: absent or with qumulo_factory_defaults. The captured factory Files share and / export are then left out, and the next baseline removes them from the cluster.

A removal in the file’s own qumulo_factory_defaults of a share or export the inventory declares is left out too, and qumulo_factory_defaults itself is left out when that empties it. A shared entry of the file, in a flat list, loses only the tenants the inventory declares it for. When it sets tenants: all, it is written as the list of the present tenants that remain, and its comment says so: “its tenants: all is written as the list of the other tenants, which does not cover a tenant added to the inventory later”.

When the inventory defines qumulo_tenants

The file cannot hold the captured qumulo_tenants then, so adoption judges what each captured tenant holds against the inventory’s, entry by entry, and writes what the inventory does not declare.

The baseline reads the cluster’s tenants from the cluster, not from qumulo_tenants, so adoption reads them from the captured tenants:

  • Tenant 1 is the cluster’s: the captured tenant renamed from Default, else the captured Default. An inventory entry with previous_name: Default renames it only when the cluster still holds Default, since the baseline renames a tenant only from a name the cluster holds.

  • The one tenant that a flat entry with no tenants names is the one tenant the run holds, which counts a tenant the inventory removes, as the baseline counts it until it deletes the tenant.

  • A captured tenant that the inventory renames is matched to the inventory’s entry by previous_name, and written under the new name. The match applies only when the cluster does not already hold the entry’s name, as the baseline renames nothing then.

  • tenants: all means the captured tenants, not the tenants the inventory declares. A captured shared entry with tenants: all is rewritten as the list of the cluster’s tenants, with a comment that says why, only when the inventory’s present tenants differ from the captured ones after its renames and removals; when it declares them, all means the same and is left as it is.

What adoption does for each captured tenant:

  • Each share and export of the tenant that the inventory does not declare is written in the file’s flat qumulo_smb_shares or qumulo_nfs_exports with tenants: [<tenant>]. When the inventory defines that flat variable too, the file cannot hold it, and a comment says to declare the entry under the tenant in the inventory.

  • A share or export the inventory declares with the same values is left out with the usual comment. One it declares with other values is refused, and the message names the capture’s entry after “and the capture in”.

  • A tenant the inventory does not declare gets a comment: its services and settings stay as the cluster has them. For a tenant other than one still named Default the comment adds that a rebuild from the inventory refuses the entries that name it until qumulo_tenants declares it. That includes a renamed tenant 1, since a rebuild forms Default and nothing renames it, and for it the comment says the inventory must declare it with previous_name: Default.

  • A tenant the inventory declares state: absent gets a comment, nothing of it is written, and none of its networks are refused. The baseline deletes it only once the inventory declares or claims each share and export it holds.

  • A tenant whose switches or settings the inventory declares with other values is refused. Settings compare as written, by the keys the inventory gives, not in the modules’ form. A null switch or setting in the inventory is unset, and one the capture does not hold, as on a cloud cluster, is not compared.

  • A network the tenant holds is refused unless the inventory lists it for that tenant, under the tenant’s entry or flat in qumulo_network.frontend_networks with tenant: naming the tenant, with the same values for the keys the inventory gives. The values compare as written, so a netmask of 24 against 255.255.255.0 differs. Under a tenant’s entry an omitted vlan_id counts as untagged, so the entry refuses a captured network on a VLAN; a flat listing takes no vlan_id. The baseline’s network document would otherwise remove or rewrite it.

  • The capture’s Default with state: absent, which it writes for a cluster that has no tenant 1, is not written. A comment says that a rebuild deletes the Default that a new cluster forms, and that the inventory’s qumulo_tenants has to declare it, unless the inventory declares Default already.

A network of a tenant the inventory does not declare is refused too, unless the inventory lists it, so beside qumulo_tenants: [] adoption refuses a cluster whose frontend networks belong to a tenant, as a single-tenant cluster’s belong to Default, unless the inventory lists them. When adoption refuses gives the remedy.

The clone leaves out qumulo_tenants when the target’s inventory defines it, with a comment, and writes none of the tenants’ shares, exports or networks. The documentation of the host_vars_duplicates filter says how the filter takes the captured tenants.

What is compared as the same values

The host_vars_duplicates filter compares two entries in the form the modules accept, but with no directory lookup: two spellings of one AD identity are a difference. Its documentation lists each key it compares or skips and how it compares a trustee.

A key the inventory’s entry leaves out

The file’s entry can give a key the inventory’s entry omits. What happens depends on who creates the share or export:

  • Adoption: the cluster holds the share or export already and keeps the value of each key an entry omits. The entry is still left out. When such a key holds a value that a create does not give, its comment names the key and says the cluster keeps it.

  • Clone: the target is fresh, so the baseline creates each share or export from the inventory’s entry alone, and each key it omits takes the create default. A key whose value in the source differs from that default refuses, as “with other values of <keys>, which the inventory’s entry leaves out”. A key equal to its default does not.

A key set to null counts as left out.

The host_vars_duplicates documentation lists the create defaults, as observed on Qumulo Core 7.10.3. A share’s permissions, an export’s restrictions and fs_path have no create default, so a clone refuses an inventory entry that leaves out the one the source’s entry gives.

What the adoption and the clone refuse

The adoption and the clone refuse, before they write the host_vars file, when the file would hold:

  • a network the inventory also declares;

  • a share or export the inventory declares with other values, which the message lists as the keys that differ;

  • for the clone only, a share or export whose entry gives a key the inventory’s entry leaves out, with a value other than a create gives;

  • for the adoption only, beside an inventory that defines qumulo_tenants, a captured tenant whose switches or settings the inventory declares with other values, and a captured tenant network the inventory does not list for that tenant, or lists with other values (when the inventory defines qumulo_tenants).

The adoption has written captures/<host>/host_vars.captured.yml by then, and the clone writes nothing. Each refusal entry reads as “the SMB share Projects of tenant Default, which the inventory declares in qumulo_smb_shares[0] and the file in qumulo_tenants[Default].smb_shares[1] with other values of fs_path”. The messages begin as Troubleshooting quotes them.

Two declarations both in the inventory, or both in the file, are not compared. A claim the baseline refuses for a reason of its own, such as an entry with no name, or with no tenant on a cluster of several, is left to the baseline, and so is a tenant_id other than 1, which only the cluster can resolve.

Areas and the variables they write

An area is a choice of gather_subset and of leave_out in capture_info. The names are those of the cluster_baseline role’s areas, plus replication. capture.yml reads every area. capture_info reads the areas gather_subset names, all by default. Each variable has the shape the role passes to the module that writes it, so a check run of the baseline from the file changes nothing. Lists are sorted and values canonical, so a second capture of an unchanged cluster writes the same file.

Directories

qumulo_directories holds each directory that an SMB share, an NFS export, a quota, a snapshot policy, an S3 bucket, the S3 base path (unless it is /) or a replication target names, and each directory above one, the root included. Each entry has the options directory takes.

  • A replication target directory is declared by its path alone, and no directory inside it is written: replication sets its attributes and its content’s.

  • A directory carries its ACL in qumulo_file_acls in place of its mode when the mode cannot express the ACL (G-FS-ACL-MODE). The entry in qumulo_directories then has no mode.

  • A directory in a spoke root, and a directory that a share, export, quota or policy names but that does not exist, is left out.

Tenants

Qumulo marks the multitenancy REST API as preview in Qumulo Core 7.10.3 and 7.11.0. The collection manages tenants through it on those releases, and a later Qumulo Core release may change it.

The tenants area runs after network, smb and nfs, which hand it what each tenant holds. It writes qumulo_tenants on every cluster that offers the tenant list, by tenant name and never by id, sorted by name. A cluster with one tenant has one entry. No tenant id is written anywhere in a capture. Each entry holds:

  • name, previous_name: Default when tenant 1 has another name, so that a replay onto a newly formed cluster renames its Default, and the six switches. A cluster without tenant 1 is noted, and what is written depends on its networking:

    • On networking the host manages (no managed interfaces, only HOST networks), the one tenant that holds a network gets previous_name: Default and no Default entry is written, when every network has a tenant, no tenant is named Default, the network, smb and nfs areas are read, and that tenant has no / export that the capture leaves out (G-MAPTO). A rebuild from the capture then renames the Default the new edge forms with to that tenant, which keeps the HOST network in tenant 1 through the rebuild. smb_files_share in qumulo_factory_defaults is present instead of absent when the capture writes a share named Files (any case) for that tenant, and nfs_root_export when it writes that tenant’s export at /. A clone keeps the previous_name, so a fresh target’s Default is renamed to that tenant.

    • Otherwise, a Default entry with state: absent, which has a rebuild delete the Default the new edge forms with. A cluster whose one tenant that holds a network has a / export that the capture leaves out (G-MAPTO) gets this form too; Rebuilds says why. No entry is written when another tenant is named Default, or when a replay of what the capture wrote could not delete Default.

    • The tenant 1 note in left_out says which of these the capture did, which factory keys it set, and, when the rename’s other conditions hold but two or more tenants hold networks or that tenant has a / export the capture leaves out, why it wrote Default absent instead; in the first case it adds that a rebuild needs qumulo_management_network, which the capture does not write. Rebuilds says why a rebuild keeps the HOST network in tenant 1.

  • networks, the tenant’s frontend networks without a tenant id, [] for a tenant with none, when the network area is read. A network on a frontend VLAN has vlan_id, and mtu when the VLAN sets one. managed_interfaces is written without the VLANs that carry only tenant networks, and the frontend bond’s network list without tenant networks;

  • smb_settings and nfs_settings, when the smb or nfs area is read: inherit for a tenant with no override, and the override’s full record for one with it, an override equal to the global settings included;

  • smb_shares and nfs_exports, each left out when empty. The factory Files share and / export stay under tenant 1. qumulo_factory_defaults is still written, present when tenant 1 holds the factory share or export.

Three things go elsewhere:

  • A share or export identical in two or more tenants becomes one entry of qumulo_smb_shares or qumulo_nfs_exports. Copies compare as the module’s input without the tenant or the id, SMB names without regard to case, and each name’s copies group by identical content. A group of every tenant on the cluster is written with tenants: all, and any other group with its tenants as a list sorted by name, and the name spelled as its first tenant spells it. Shared entries are sorted by name, then by their first tenant. Every other copy goes under its tenant, and the factory share and export never merge.

  • A network of the backend bond, or that no tenant holds, goes in qumulo_network.frontend_networks. Capture notes a backend network a tenant holds on a cluster with two or more tenants, which a replay onto a rebuilt cluster refuses while a tenant holds it, and an unbound network on such a cluster. A rebuild whose replay has several tenants refuses, in its preflight, an unbound network that the newly formed edge lacks (on managed networking, any network but 1; on host-managed networking, none, since the replay’s tenant 1 pass writes every network sent with no tenant first), and otherwise puts it in tenant 1, which the preflight reports as drift; A network sent with no tenant says when.

  • On a cloud cluster, which capture knows from the protection type, the six switches are left out of every entry and noted once, since no cloud cluster supports a tenant write.

Capture also notes a VLAN that carries the networks of two tenants, or a tenant’s network and one no tenant holds. For two tenants on one VLAN, the baseline warns about the layout on the cluster that was captured and goes on, and refuses it on a cluster that does not hold it yet, as a rebuild. A VLAN that carries a tenant’s network and an unbound one stays in managed_interfaces, beside the vlan_id on the tenant’s network, so a check run from a capture with the tenants area refuses it as a VLAN declared in two places; without the area, the baseline keeps it on the captured cluster. A rebuild whose replay has several tenants refuses the unbound network in its preflight when the newly formed edge lacks it (on managed networking, any network but 1), and otherwise puts it in tenant 1 (why). A tenant on an identity configuration other than tenant 1’s is written in full, and only its identity is noted, as per-tenant identity is not supported yet. Capture never writes identity.

The network, smb, nfs and tenants areas read the tenant list, and the smb and nfs areas read each tenant’s override, so the user the play connects as needs PRIVILEGE_TENANT_READ. A refusal of the list with HTTP 403 fails the capture, as a 403 does on every read but the key store’s and the keytab’s. A cluster that does not offer the list, which a release without the multitenancy API does not, lists tenants in unavailable_subsets and notes it, and the other areas write the flat forms below.

The kerberos area reads the keytab, and the cluster returns every key of it to the user that reads it, which needs PRIVILEGE_KERBEROS_KEYTAB_READ. When the user the play connects as lacks it, as the built-in Observers role does (Qumulo Core 7.11.0), the area still writes qumulo_kerberos, leaves out the keytab’s supply line, and says so in one entry under left_out. Capture writes and returns no key.

Left out

Effect

network

No tenant entry has networks.

network.floating_ips

The floating ranges of every tenant network are dropped.

smb

Every share and every SMB override, nested or shared, is dropped.

nfs

Every export and every NFS override, nested or shared, is dropped.

S3

  • qumulo_s3_settings holds the base path, and qumulo_directories holds the base path’s directory.

  • qumulo_s3_buckets holds the buckets outside the spoke roots, and qumulo_directories their directories.

  • qumulo_s3_bucket_policies holds one entry per kept bucket that has a policy, with each principal in the trustee grammar the inventory uses. A policy whose principals cannot be converted is left out with a note.

  • qumulo_s3_access_keys holds each key by its user and access_key_id. The cluster returns a key’s secret only to the request that makes the key, so each key is named under the secrets to supply (G-S3-KEY). After a rebuild the baseline makes a new key and writes its secret under the host’s artifact directory.

Serve a directory as an S3 bucket has the steps.

Values only a peer records

A spoke records the hub’s addresses but not its own, a hub records the spoke’s but not its own, and a replication source records the address it reaches the target at (G-PORTAL-HOSTS). capture_info therefore returns, for each peer, what this cluster records of the peer’s own variable in capture.peer_values. capture.from_peers lists the variables of this cluster that only its peers record.

Shape of the files

host_vars_text renders both files.

  • The file starts with the header as comments, then the variables sorted by name, then the secrets to supply, then what was left out.

  • Every comment line is wrapped at 112 characters of text and starts with # .

  • Every string value is tagged !unsafe, so Ansible reads it as written and never templates it. A share description with a Jinja expression in it therefore does not run on the controller.

  • Mapping keys, mappings and sequences carry no tag.

  • A string that would read as another type without its tag, such as 0777 or true, is written quoted without the tag. The empty string is written as '' without the tag.

  • A template you add to the file yourself, such as a reference to a vaulted secret, is evaluated as usual.

  • Each secret to supply is a comment: # <variables>: and then the reason, indented. Lines with the same reason share one heading.

  • Each item left out is a comment: # <what>: and then the reason, indented.

The host file’s header is the first three lines of the sample. The capture file’s header reads “Captured from <host> by playbooks/capture.yml” and says that it is a one-time import.

Clone

A clone gives a fresh cluster (the target) the configuration of another cluster (the source). It reads the source, changes nothing on it, writes the target’s host_vars file, and runs the cluster_baseline role on the target. It copies configuration only, never data. The target is a second cluster with a name of its own, and the clone never claims to be the source.

Variables the target’s inventory defines

A host_vars file outranks the inventory’s other variables, so the clone leaves out each variable the target’s inventory already defines, with a note, and removes its supply lines.

The exception is a mapping that holds only the variable’s secrets. qumulo_ad with only join_user and join_password, qumulo_kerberos with only keytab or keytab_path, qumulo_monitoring with only nexus_join_key, and qumulo_capacity with only license_document each keep the source’s other settings in the file. The first pass takes those secrets from the inventory, but the file’s variable outranks the inventory’s from then on, and the note says to move the secrets into the file.

  • A mapping key counts only when its value is not empty (an empty string, list or mapping, false and 0 are empty). An empty mapping, or one that holds only empty placeholders, therefore counts as holding only the variable’s secrets, and the source’s settings are kept.

  • A variable that the clone’s own existing file holds does not count as one the inventory defines. A second run therefore writes the same file.

The target’s qumulo_cluster_name in the inventory must equal clone_edge_name, or the clone fails.

A variable the inventory defines that the file does not hold stays in force beside the file, so the clone leaves out each share or export entry the inventory also declares, and refuses one it declares with other values; see Declared again by the inventory. The clone drops qumulo_network and each tenant’s networks, so it never declares a network twice. On a re-run, the variables an earlier clone’s file holds are that file’s, not the inventory’s, so the second run decides as the first did.

What the first pass needs

clone_host_vars returns first_pass_needs: the supply lines the first baseline cannot do without, minus those named in clone_edge_supply and those the inventory gives.

  • a password for each local user the target lacks and that is present in the file, since a user is created with one;

  • the join credentials while the target is not joined to the file’s domain.

The other secrets guard what the first pass skips or hands off. The clone writes the file, then fails naming each missing secret and changing nothing on the target. A Nexus join key given in clone_edge_supply registers the target in the same pass. Without a join key or qumulo_nexus_api_token, the first pass skips registration without a message.

What the clone checks

Every refusal comes before anything changes on the target, except the missing-secret one, which follows the write of the file. A clone_edge_check_only run refuses a target whose inventory declares qumulo_portal or qumulo_replication_relationships.

The check that the target is fresh reads the shares and exports nested under the target’s tenant entries and the flat lists’ shared entries, beside the flat entries. The target’s capture reads the tenants area for it. The tenant formation creates is the target’s only tenant, or else the one named Default or renamed from it. Only that tenant’s factory Files share and / export are exempt. Every other tenant counts as configuration the target holds, as does every other share or export under any tenant, so a target with a second tenant is refused unless clone_edge_allow_configured_target is true. The refusal names each, as “the tenant finance” or “the SMB share ledger of tenant finance”.

After the target’s checks and before the file is rendered, the clone leaves out the shares and exports the inventory declares too, and refuses one the inventory declares with other values (Declared again by the inventory); nothing is written.

Troubleshooting: cloning lists each refusal with its message.
