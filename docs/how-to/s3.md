# Serve a directory as an S3 bucket

This page declares a cluster's S3 settings, a bucket, its policy and an access key in the inventory, applies them with
the baseline, and takes the key's secret from the file the run writes.
When you finish, an S3 client holding that key can reach the bucket, and a second run of the baseline reports no
change.

## Before you start

- Set up the inventory: [Set up an inventory for your clusters](set-up-inventory.md).
- Declare the cluster's users in the inventory, or have them on the cluster.
  A policy names its principals, and a key names its user, and the cluster refuses a name it does not know.
  Local users and groups come before S3 in the baseline's order.
- Declare the S3 variables on the host whose file system holds the bucket's directory.
  On an edge, that is only outside every portal spoke root; a path under one is the hub's, so declare it on the hub
  ([why](../explanation/edges-and-portals.md#spoke-roots-hold-the-hubs-data)).
- Have a place for secrets.
  The key's secret is written to a file on the controller, in a directory beside the inventory source.
  Keep that directory out of version control.

## Declare the settings, a bucket, its policy and a key

Put the S3 variables in the host's `host_vars` file, with the bucket's directory declared in `qumulo_directories`:

```yaml
# host_vars/hub01.yml
qumulo_directories:
  - {path: /data/photos, owner: 'local:svc-photos', mode: '0750'}
qumulo_s3_settings:
  enabled: true
  secure: true
  multipart_upload_expiry_interval: 1weeks
qumulo_s3_buckets:
  - {name: photos, path: /data/photos, versioning: Enabled}
qumulo_s3_bucket_policies:
  - bucket: photos
    policy:
      Statement:
        - {Effect: Allow, Principal: {Qumulo: ['local:svc-photos']}, Action: [s3:GetObject, s3:PutObject, s3:ListBucket]}
qumulo_s3_access_keys:
  - {user: 'local:svc-photos'}
```

- The baseline applies the settings, the buckets and the policies in step 19, after the NFS exports, and the keys last,
  in step 22 ([order of areas](../explanation/architecture.md#the-order-of-areas)).
- Give the directory the owner and mode its S3 users need.
  S3 writes only where the file system lets the key's user write.
- A policy principal is a trustee: `Everyone`, `local:svc-photos`, `ad:CORP\Photographers`, `uid:1000` or
  `sid:S-1-5-21-1-2-3-1001`.
  A bare name is refused.
- A policy has no `Resource` key: a statement applies to its own bucket.

Every option of the four modules, [s3_settings](../../plugins/modules/s3_settings.py),
[s3_bucket](../../plugins/modules/s3_bucket.py), [s3_bucket_policy](../../plugins/modules/s3_bucket_policy.py) and
[s3_access_key](../../plugins/modules/s3_access_key.py), is in `ansible-doc qumulo.cluster.<module>`, and the variables
are in [Inventory variables](../reference/variables.md#s3).

## Apply it

1. Preview the run, with the diff:

   ```sh
   ansible-playbook qumulo.cluster.baseline -i inventory -l hub01 --check --diff
   ```

   The check run reports the bucket, the policy and the key as changes.
   A key that would be made is shown without a secret.
2. Apply it:

   ```sh
   ansible-playbook qumulo.cluster.baseline -i inventory -l hub01
   ```

   The run ends with a message for each key it made, naming the key's user and id and the file that holds its secret.
3. Take the secret from that file and give it to the key's consumers.
   The cluster shows a secret only when it makes the key, so the file is the copy to keep
   ([G-S3-KEY](../reference/gaps.md), [why](../explanation/state-management.md#values-the-cluster-shows-once)).
   The file is `<cluster_baseline_artifact_dir>/<host>/secrets/s3-<user>-<access_key_id>.yml`, in a directory and a
   file readable only by their owner.
   It holds `user`, `access_key_id` and `secret_access_key`.
   Characters of the user other than letters, digits, `.`, `_` and `-` become `_` in the file name.
4. Declare the key's id, quoted, in its entry before the next run:

   ```yaml
   qumulo_s3_access_keys:
     - {user: 'local:svc-photos', access_key_id: '00000000000003e8b5a2'}
   ```

   Quote the id: an id of digits only would otherwise be read as a number.
   An entry with only `user` cannot tell a key whose secret its consumers hold from one whose secret was lost.
5. Check that the cluster and the inventory agree.
   Run the check again; it reports no change:

   ```sh
   ansible-playbook qumulo.cluster.baseline -i inventory -l hub01 --check --diff
   ```

   To read what the cluster holds, run `qumulo.cluster.s3_info` and look at `s3.buckets`, `s3.policies` and
   `s3.access_keys`.
   It never returns a secret.

## Create the bucket's directory with the bucket

To let the bucket create its directory, set `create_fs_path: true` on the bucket instead of declaring it in
`qumulo_directories`:

```yaml
qumulo_s3_buckets:
  - {name: scratch, path: /data/scratch, create_fs_path: true}
```

The cluster chooses the modes of a directory made this way.
The bucket uses `create_fs_path` only when it creates the bucket.
Without it, `s3_bucket` refuses a missing directory before it writes.

## Change a bucket's policy

The policy you declare is the whole document.
A statement the declaration leaves out is removed from the cluster.
Edit the `policy` and run the baseline; a `--check --diff` run shows the policy before and after.

To remove a bucket's policy, give its entry `state: absent`:

```yaml
qumulo_s3_bucket_policies:
  - {bucket: photos, state: absent}
```

A policy that takes away the connecting user's own right to change the policy is refused, unless the entry sets
`allow_remove_self: true`.

A declaration in either spelling of a principal reports no change: `Everyone` and the `world:Everyone` the cluster
reads back are the same principal
([why](../explanation/state-management.md#comparing-in-the-form-the-cluster-reads-back)).

## Remove a bucket

Set `state: absent` on the bucket:

```yaml
qumulo_s3_buckets:
  - {name: photos, state: absent}
```

Deleting the entry from `qumulo_s3_buckets` removes nothing: the bucket stays on the cluster.

- The bucket's directory and every object in it stay.
  A bucket declared again at the same path serves them again.
- The bucket's policy goes with it on the cluster.
  Remove the bucket's entry from `qumulo_s3_bucket_policies` in the same change, or give it `state: absent`.
  A policy entry for a bucket that is gone fails the run, after the buckets and before the quotas, snapshot policies,
  replication and keys; a check run reports only a note.
- The cluster removes no bucket that has an unfinished multipart upload.
  The module fails, in check mode too.
  To abort the uploads first, which loses what they held, set `allow_data_loss: true` on the entry.

## Move a bucket to another directory

A bucket's directory cannot change once the bucket exists, and a different `path` fails before any write ([G-S3-PATH](../reference/gaps.md)).
To move one:

1. If the objects must move too, move them in the file system, since removing a bucket does not touch them.
2. Remove the bucket with `state: absent`, and give its entry in `qumulo_s3_bucket_policies` `state: absent` too, or
   take the entry out.
3. Declare the bucket again with the new `path`, and declare its policy again.
   Removing the bucket removed the policy.

## Replace an access key

A user holds at most two keys.
The collection makes the new key only after the old one goes, since the cluster takes no name for a key and a
declaration can name only a key that exists ([G-S3-ROTATE](../reference/gaps.md)).
The consumers lose access from the removal until they hold the new secret.
Plan the change for a time when that is acceptable.

If the user holds another key that no entry declares, declare it by its id first.
Otherwise the run fails and names the keys the user holds.

1. Remove the old key by its id, and keep the entry that declares it:

   ```yaml
   qumulo_s3_access_keys:
     - {user: 'local:svc-photos', access_key_id: '00000000000003e8b5a2', state: absent}
   ```

   The step runs removals first, so a user at the limit of two can be given a new key in the same run.
2. Add a second entry that names the same id, without `state`:

   ```yaml
   qumulo_s3_access_keys:
     - {user: 'local:svc-photos', access_key_id: '00000000000003e8b5a2', state: absent}
     - {user: 'local:svc-photos', access_key_id: '00000000000003e8b5a2'}
   ```

   After the removal the user holds fewer keys than its entries declare, so this entry makes a new key.
   An entry that names no id would not: any key the user still holds satisfies it.
3. Run the baseline.
   It removes the old key, makes a new one and writes the secret to its file.
4. Replace the two entries with one that names the new id, quoted, and give the secret to the consumers.

## Make the keys again after an edge rebuild

A rebuilt cluster holds none of the old keys, and no route imports one.
The rebuild preflight refuses to destroy a cluster that holds any key unless `s3_keys` is in `edge_rebuild_acknowledge`
([Rebuild an unprotected edge](edge-rebuild.md)).

1. Spell the user the same way in every entry, and give every entry an id.
   A rebuild restores only the keys whose entries declare an id, and counts `local:svc` and `LOCAL:svc` as two users
   ([G-S3-KEY](../reference/gaps.md)).
2. Rebuild the edge as that page shows.
   The replay's baseline makes a new key for each entry that declares an id and writes each secret to a file under
   `<edge_rebuild_artifact_dir>/<host>/secrets/`.
3. Read the rebuild report ([Work through the report](edge-rebuild.md#work-through-the-report)).
   It is written even when a step fails.
   It names each key the replay made, with the file of its secret, and each key entry that failed.
4. Give each new secret to the consumers.
   Every S3 client needs the new secret.
5. Replace each old id in `qumulo_s3_access_keys` with the new id, quoted.
   A run that still names an old id fails and names the keys the user holds, rather than make more.

## Run the key module without the baseline

`qumulo.cluster.s3_access_key` run in a task of your own needs `secret_destination`, a directory on the controller to
write the file in, and `no_log: true` on the task, since the task's result holds the secret.
Without either, a task that would make a key fails before any write, in check mode too.

```yaml
- name: Give the backup service an S3 key, writing a new key's secret to a file
  qumulo.cluster.s3_access_key:
    user: local:svc-backup
    secret_destination: "{{ inventory_dir }}/../artifacts/{{ inventory_hostname }}/secrets"
  register: backup_key
  no_log: true
```

`s3_access_key` has a recipe for each of the other cases.
Any task that reads `backup_key.secret_access_key` needs `no_log` too.

## Adopt a cluster that already serves S3

`playbooks/capture.yml` writes the S3 variables from the cluster.
The steps are in [Adopt a cluster you already run](adopt-a-cluster.md), and
[what capture writes for S3](../reference/capture-and-clone.md#s3) is in the reference.

The keys need nothing supplied: their consumers already hold the secrets, and the captured `access_key_id` keeps each
key.
Declare by hand any policy capture left out because its principals could not be converted to trustees.

## If a run stops

- A bucket whose directory is missing fails before it writes.
  Declare the directory in `qumulo_directories`, or set `create_fs_path: true`.
- A bucket under a spoke root fails before anything is written, in step 2, and the module refuses it too.
  Declare the bucket on the hub.
- A versioning or lock change the cluster cannot make fails before it writes, in check mode too
  ([G-S3-LOCK](../reference/gaps.md)): versioning back to `Unversioned`, removing a lock, a locked bucket without
  versioning `Enabled`, or `default_retention` without `object_lock`.
  `ansible-doc qumulo.cluster.s3_bucket` has the rules.
- A policy names a principal that does not exist yet, or a bare name, and fails.
  Create the user first, and write the principal as a trustee.
- A key entry that failed does not stop the others.
  The step fails after its last entry and names each entry that failed.
- A key entry that would make a key fails when the run has no artifact directory.
  A host that comes from no inventory file or directory on disk, as one given with `-i hub01,`, has none: set
  `cluster_baseline_artifact_dir` to a directory, or `secret_destination` on the entry.
- A policy entry for a bucket that is gone fails the baseline.
  Remove the entry or give it `state: absent`.

[Respond to a refusal](respond-to-a-refusal.md) covers refusals in general.
