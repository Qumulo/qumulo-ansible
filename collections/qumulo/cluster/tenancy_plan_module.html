qumulo.cluster.tenancy_plan module – Check a cluster’s tenants, networks, shares and exports before the baseline writes any of them

Note

This module is part of the qumulo.cluster collection (version 0.1.0).

It is not included in ansible-core. To check whether it is installed, run ansible-galaxy collection list.

To install it, use: ansible-galaxy collection install qumulo.cluster.

To use it in a playbook, specify: qumulo.cluster.tenancy_plan.

Synopsis

  • Computes step 2 of the qumulo.cluster.cluster_baseline role for network tenants. From the inventory’s tenants, networks, shares and exports and what step 2 read from the cluster, it works out what steps 3a, 3, 3b, 18, 19 and 20a will send, and which rules the inventory breaks or the continuity rule would.

  • A pure computation. It sends no request, takes no connection options, and is not in the qumulo.cluster.qumulo action group, so module_defaults for that group do not reach it.

  • Every name is judged as it will be after the renames of step 3a, which tenants[].previous_name declares.

  • The module judges the inventory in six stages, in that order, and stops after the first stage that refuses, because each stage reads what the one before it built. The stage reports every refusal it finds, in refusals, and the module then fails with their messages, one to a line, in msg, beside refusals, and carries nothing else of the plan. At Ansible verbosity 3 or more (-vvv) the failure also carries plan, what the module had computed before it stopped. A refusal of a later stage shows only once the earlier stages pass.

  • Stage 1, renames. An entry that renames a tenant to a name the cluster holds is refused when another present entry renames from that name, as in a swap or a chain, since the first rename would find the name taken. An entry without such a follower records a rename already done, and is not refused. Two present entries that rename one cluster tenant are refused.

  • The cloud refusal comes straight after stage 1, before every other rule. The module refuses every tenant write that the run would send to a cloud cluster, whether a rename, a create, a switch change or a delete, in one message that lists them, since no cloud cluster supports tenancy (G-TENANT-CLOUD). A cluster is cloud when cluster_kind is cnq, or, with it unset, when cluster.protection_type is object-backed. edge and baremetal, another protection type, and none are not cloud. allow_management_disruption does not skip this refusal. It ends the plan, so no other rule and no verdict runs, and plan is empty. The network PUT is no tenant write, and a run that makes only that is not refused.

  • Stage 2, entries and references. A tenant declared twice, a tenant with tenants[].identity, a key in a dict tenants[].smb_settings or tenants[].nfs_settings other than the server settings of qumulo.cluster.smb_settings or qumulo.cluster.nfs_settings, so tenant and state too, and a run that would delete every tenant are refused. So is a create of a tenant while tenant 1 is gone and the cluster’s tenants use different identity configurations, since the new tenant takes tenant 1’s or the one they share. So is a create that makes the cluster’s second tenant while a tenant holds a network that is not on the frontend bond, a frontend VLAN or a HOST network (G-TENANT-BACKEND). A share, export or network that names a tenant that neither tenants declares nor the cluster holds is refused, and so is a network that names a tenant declared absent.

  • Stage 3, shares and exports. A (tenant, name) pair that two entries claim is refused, whether the entries are nested under a tenant, shared, or the factory share or export that factory_defaults removes, and whether they claim it present or for removal. A tenant declared absent that holds a share or export that no entry declares or claims for it is refused, and the message lists each (G-TENANT-CASCADE). The rules of smb_shares, nfs_exports, tenants[].smb_shares and tenants[].nfs_exports on an entry’s own form, such as a missing name or a malformed tenants, and of tenants[].smb_settings and tenants[].nfs_settings, refuse in this stage too. The rules on which tenants an entry names refuse in stage 2.

  • Stage 4, NFSv4.1. The module refuses a global NFSv4.1 enable while a tenant the run keeps, declared or not, has two export paths that nest after the run’s removals, and a tenant that serves NFSv4.1 at the end of the run while two of its export paths nest, when the run changes that tenant’s NFSv4.1 setting or exports. A tenant declared absent is not judged, since the run removes its exports first.

  • Stage 5, networks. A network listed more than once, or listed under a tenant declared absent and also kept in network.frontend_networks without a tenant, is refused. So is a tenant on a network of the backend bond (G-TENANT-BACKEND), and a document that gives networks of two tenants to one interface or VLAN, two networks of one address family to one VLAN, two tenants[].networks[].mtu values to one VLAN, or a VLAN that is declared in more than one place. On networking its host manages, a tenant network with tenants[].networks[].vlan_id or of type STATIC is refused. So is a new flat network with no tenant when the run has more than one tenant. So is a cluster VLAN that carries a network the run keeps but the derived interfaces put on no interface, as when a tenant network’s VLAN, derived from its tenants[].networks[].vlan_id, would leave out the other network the VLAN carries. A removed network that a tenant holds which tenants does not declare is refused only once a present entry of tenants declares tenants[].networks. With network.frontend_networks alone the run removes a network as qumulo.cluster.network_config does. A network that a tenant declared absent holds and the run keeps is refused, also when the run builds no document or does not own networks. Without networks in owned_parts, a present tenant whose tenants[].networks is not empty is refused, and so is a listed network that the cluster lacks, with the inventory entry named, since such a run sets only floating addresses. A conflict that the cluster already holds, as another writer left it, is warned of and not refused. When the run writes a network document (network_changes is true), the stage also refuses a planned document in which two or more STATIC networks carry a default gateway of one IP version, as qumulo.cluster.network_config does, with the same message. The cluster refuses it on chassis nodes at step 3, after step 3a has created the tenants. Networks that the cluster already gives each a gateway of that version are warned of, not refused. The checks of this stage run in groups, and a group that refuses ends the stage.

  • Stage 6, writes and continuity. The module lists the tenant writes and the network PUT that the run makes, in the order of the baseline’s steps. They are step 3a’s renames, then its enables, then its creates, step 3’s network PUT when network_changes is true, step 3b’s disables, and step 20a’s deletes, each group in the order of tenants. It then judges each judged write on the management network and the bindings as they will be immediately after that write, so that a run which would cut the play off from the cluster is refused before any write.

  • A create, a delete, the network PUT and a change of rest_api_enabled or web_ui_enabled are judged. A rename and a change of any other switch are not, except that a rename that also turns on a REST switch is one item, judged as that change. A run that makes no judged write is not judged, and needs neither the management network nor the status.

  • After a judged write the management network must belong to a tenant with REST enabled. With one tenant after the write the management network is not looked up, and the only tenant must have REST enabled. The document in force after a write is the cluster’s current one for a write at step 3a, the planned one for step 3 and every later write, and the current one when the run sends no network PUT.

  • REST enabled depends on the port the cluster listens on for the play, cluster_port. With 443 it means web_ui_enabled, since the play then reaches REST through the web UI listener, and with another port it means rest_api_enabled. Without cluster_port the cluster-side port is taken to be api_port, except that api_port 443 fails closed, so REST enabled then means that both switches are on.

  • The management network is a set of network ids within the document in force. It is management_network when that is set, which the module takes as the operator’s word. Otherwise it is, for each address that api_host resolves to on the controller, the network whose ranges hold it in the document in force. An address that no range holds, or that a HOST network’s ranges hold, needs cluster.status, which places the address on a network. With two or more tenants after the write, a HOST network in the set must also show on a device of a node in cluster.status, unless management_network declares it and the status is unavailable.

  • When the management network is needed, with two or more tenants after the write, and it is undetermined, or a network in it is held by no tenant or is on no device, the refusal is the first of these that applies. (1) The cluster is host-managed and has no frontend network yet. (2) The run removes a network of the set. (3) management_network names a network that is neither on the cluster nor in the inventory; when the run itself adds that network and the write is judged before step 3, as a create at step 3a is, the message says to add the network in an earlier run. (4) A network of the set belongs to no tenant. (5) api_host resolves to no address, no network carries it, or the status is needed and unavailable (G-NET-APPLY). (6) A HOST network of the set is not on the cluster yet, or the status shows it on no device.

  • The other refusals of a judged write are the plain breach, where the management network after the write belongs to a tenant without REST enabled, or the only tenant lacks it, and the fail-closed breach, where cluster_port is unset, api_port is 443 and exactly one of the two switches is on. Each message gives its remedy in the inventory’s words, such as qumulo_management_network for management_network and qumulo_cluster_port for cluster_port.

  • A caller passes the cluster’s network status in cluster.status, or why it is unavailable in cluster.status_unavailable, whenever the cluster holds two or more tenants or the run creates a tenant, a present entry whose name and previous_name the cluster both lack, which covers every run that can need it. A run that needs the status and has neither fails with an internal error that asks for a bug report.

  • When step 3 writes a network document, the module also checks that the document keeps the address of api_host, when that is an IP address that a range of the current document holds, as qumulo.cluster.network_config does at step 3. A document that drops it is refused, unless allow_management_disruption is set and api_host_after names the address that later tasks connect to. The message names step 3, asks for qumulo_api_host_after, and for qumulo_allow_management_disruption when that is not set, and says that this play connects to the address. A name in api_host is not checked here.

  • Each warning is printed, and none stops the run.

Parameters

Parameter

Comments

allow_management_disruption

boolean

The inventory’s qumulo_allow_management_disruption.

true skips every verdict of stage 6 for the whole run, so verdicts is empty and no item carries management_network, planned_networks or planned_tenants. A delete still carries content_removed.

It does not skip the cloud refusal, or the address check of step 3, which, when the document drops the address of api_host, then needs api_host_after.

Choices:

  • false ← (default)

  • true

api_host

string / required

The address or name the play connects to, from qumulo_api_host.

The module resolves a name on the controller, where modules run, to find the management network when management_network is unset and a judged write needs it. A name that resolves to no address is refused then. For an IP address, step 3’s address check asks that the new document keeps it.

api_host_after

string

The inventory’s qumulo_api_host_after, the address that later tasks connect to once step 3 has changed the address of api_host.

With allow_management_disruption it lets step 3’s document drop the address of api_host.

api_port

integer

The port the play connects to, from qumulo_api_port, which is 8000 unless the play sets another.

Without cluster_port it is also the cluster-side port, and 443 then fails closed, so REST enabled means both switches on.

Default: 8000

qumulo.cluster.cluster_info‘s protection.protection_system_type. The module reads it only when cluster_kind is unset.

status

list / elements=dictionary

qumulo.cluster.network_info‘s status subset, a list with one entry for each node, when step 2 read it and it answered.

Stage 6 reads from it the network that carries an address no range holds, and the HOST networks that show on a device. A caller passes it, or cluster.status_unavailable, whenever the cluster holds two or more tenants or the run creates one. A create is a present entry whose name the cluster lacks once the run’s renames are made, so a rename is not one, and an entry that takes the name a rename frees is.

Giving it with cluster.status_unavailable fails the module. A run that needs the status and has neither fails with an internal error.

status_unavailable

string

Why qumulo.cluster.network_info‘s status subset is unavailable, when step 2 read it, as that module lists it in unavailable_subsets. The Qumulo Core container answers HTTP 500, and some releases do not offer the status (G-NET-APPLY). The text is not used in a message.

With it, a declared management_network is trusted without the HOST device check, and an undeclared one that needs the status is refused.

cluster_kind

string

The inventory’s qumulo_cluster_kind. cnq marks a cloud cluster, and edge and baremetal an on-premises one.

Unset, cluster.protection_type tells. The module refuses every tenant write to a cloud cluster, straight after stage 1.

Choices:

  • "cnq"

  • "edge"

  • "baremetal"

cluster_port

integer

The inventory’s qumulo_cluster_port, the port the cluster listens on for the play.

It picks the switch that REST enabled means in stage 6, web_ui_enabled for 443 and rest_api_enabled for another port. Unset, the cluster-side port is api_port, and 443 fails closed.

factory_defaults

The inventory’s qumulo_factory_defaults.

Default: {}

nfs_root_export

string

As factory_defaults.smb_files_share, for tenant 1’s factory / export and nfs.removals.

Choices:

  • "absent"

smb_files_share

string

absent adds the removal of tenant 1’s factory Files share to smb.removals, and claims that pair, also when tenant 1 is declared absent. The module only warns when the cluster has no tenant 1.

present, or unset, does nothing. When tenant 1 is declared absent and the cluster holds the share, the share counts as tenant 1’s content, which tenant 1’s entry must declare, or the stage 3 leftover rule refuses the run, and present then also draws a warning that the option has no effect.

Choices:

  • "present"

  • "absent"

list / elements=integer

The inventory’s qumulo_management_network, the ids of the networks that the play reaches the cluster on.

Stage 6 takes it as the management network of each judged write that leaves two or more tenants, as the operator’s word, so it needs no status. An id the document in force lacks is refused, and an empty list fails the module when a judged write needs the management network.

owned_parts

The parts of the network document the role passes qumulo.cluster.network_config in owned_parts. The module merges step 3’s document for these parts, and derives the frontend VLANs and the frontend bond’s networks only when interfaces is among them.

The tenants’ networks, and any removal or move of a network, need networks.

  • "networks" ← (default)

smb_shares

list / elements=dictionary

The inventory’s qumulo_smb_shares, each entry the options of qumulo.cluster.smb_share, with tenants naming the tenants it applies to.

tenants is a list of tenant names, or all for every tenant tenants declares present. The entry claims the share in each listed tenant that is not declared absent, and for removal in each that is, which for all is every absent tenant. A tenant that leaves an explicit list keeps its copy until an entry with state=absent claims it.

tenant_id, deprecated, counts as tenants naming that tenant, with a warning, and an id that no tenant has skips the entry, with a warning. It is refused beside tenants. tenant is refused.

An entry with neither names the cluster’s only tenant. It is refused when the run has more than one tenant, which are the cluster’s after the renames and the run’s creates.

An entry that gives no share_name, an empty tenants, one that names a tenant twice, one that is neither a list nor all, and all with no present tenant declared are refused.

Default: []

tenants

list / elements=dictionary

The inventory’s qumulo_tenants.

Entries are matched to the cluster’s tenants by name. A present tenant that the cluster lacks counts as one that step 3a creates.

Default: []

any

Reserved for per-tenant identity. Any value is refused.

A non-empty list needs networks in owned_parts.

smb_settings

any

The tenant’s SMB override. A dict is the options of qumulo.cluster.smb_settings, and smb.overrides gets an item with present for it. inherit removes the override, with an item for it too.

Unset leaves the override alone. Anything else is refused, and so is a key of a dict other than the server settings of qumulo.cluster.smb_settings, so tenant and state too, with the nearest key in the message when there is one. A key refused so is refused under a tenant declared absent as well; otherwise the value is ignored there.

Attributes

Attribute

Support

Description

check_mode

Support: full

This action does not modify the cluster.

Can run in check mode and return a changed status prediction without modifying the cluster.

diff_mode

Support: none

This action does not modify the cluster.

Will return details on what has changed, or would change in check mode, when in diff mode.

idempotent

Support: full

This action does not modify the cluster.

When run twice in a row outside check mode with the same arguments, the second run reports no change.

This assumes that nothing else changed the cluster in between.

Notes

Note

  • API: none.

  • This module plans writes to the multitenancy REST API, which Qumulo marks as preview; a later Qumulo Core release may change it.

  • Registers: G-TENANT-BACKEND, a tenant on a backend network, which stages 2 and 5 refuse; G-TENANT-CASCADE, the shares and exports a deleted tenant takes with it, which stage 3 refuses to leave unclaimed; G-TENANT-LISTEN, the rebind of every listener, which stage 6 judges on each write; G-NET-APPLY, the network status that the Qumulo Core container answers with HTTP 500, which stage 6 reads as unavailable; G-TENANT-CLOUD, the cloud platforms that refuse every tenant write, which the module refuses straight after stage 1.

Examples

# tenancy_plan takes no connection options. The first four tasks read the cluster as step 2 does, so set the connection
# once for the play with module_defaults for group/qumulo.cluster.qumulo, or in the QUMULO_* environment variables.
- name: Read the cluster's tenants
  qumulo.cluster.tenant_info:
  register: tenant_facts

- name: Read the cluster's network document and its network status
  qumulo.cluster.network_info:
    gather_subset: [document, status]
  register: network_facts

- name: Read the cluster's shares
  qumulo.cluster.smb_info:
    gather_subset: [shares]
  register: smb_facts

- name: Read the cluster's exports and NFS settings
  qumulo.cluster.nfs_info:
  register: nfs_facts

# The cluster already holds Default and finance as the inventory declares them, so refusals is empty, network_changes is
# false and step 3 sends no network document. smb.shares and smb.overrides list what step 18 applies: the home share in
# both tenants, and finance's own SMB override. A second run gives the same plan. Only Default carries a default
# gateway: the cluster takes one IPv4 default gateway, and the module refuses a second.
- name: Plan the two tenants that the inventory and the cluster already agree on
  qumulo.cluster.tenancy_plan:
    tenants:
      - name: Default
        networks:
          - id: 1
            name: Default
            type: STATIC
            netmask: 255.255.255.0
