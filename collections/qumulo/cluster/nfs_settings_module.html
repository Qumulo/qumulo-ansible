qumulo.cluster.nfs_settings module – Manage a Qumulo cluster’s NFS server settings

Note

This module is part of the qumulo.cluster collection (version 0.1.0).

It is not included in ansible-core. To check whether it is installed, run ansible-galaxy collection list.

To install it, use: ansible-galaxy collection install qumulo.cluster.

To use it in a playbook, specify: qumulo.cluster.nfs_settings.

New in qumulo.cluster 0.1.0

  • Synopsis

  • Parameters

  • Attributes

  • Notes

Synopsis

  • Sets the cluster-wide NFS server settings, or with tenant one tenant’s override of them. Options left unset keep the cluster’s values.

  • Only the settings that differ are written, in one PATCH. With tenant, a new override is created with one PUT, and state=inherit deletes the override.

Parameters

Parameter

Comments

api_host

string / required

Address or name of the Qumulo cluster’s REST API.

An IPv6 address is given bare, as fd00::5; the URL puts it in brackets.

If not set, the value of the QUMULO_API_HOST environment variable is used.

api_password

string

Password of api_username.

Set exactly one of api_password and api_token. An empty string counts as unset.

If not set, the value of the QUMULO_API_PASSWORD environment variable is used.

api_port

integer

TCP port of the REST API.

If not set, the value of the QUMULO_API_PORT environment variable is used.

Default: 8000

api_token

string

An access token, sent in place of logging in.

An access token is bound to one cluster and does not survive a rebuild.

Set exactly one of api_password and api_token. An empty string counts as unset.

If not set, the value of the QUMULO_API_TOKEN environment variable is used.

api_username

string

User that logs in with api_password.

If not set, the value of the QUMULO_API_USERNAME environment variable is used.

Default: "admin"

auth_sys_enabled

boolean

Accept AUTH_SYS authentication.

Choices:

  • false

  • true

ca_path

path

PEM file of the certificate authority that signed the cluster’s certificate.

On Python 3.13 and later this must be a CA certificate, with basic constraints.

A bare self-signed leaf certificate cannot be pinned here on Python 3.13 and later; such a cluster is reached only with validate_certs=false.

If not set, the value of the QUMULO_CA_PATH environment variable is used.

expected_cluster_uuid

string

The UUID the cluster at api_host must have.

Before the first credentials are sent, the module reads the cluster’s UUID from GET /v1/node/state, which needs no login, and fails when it differs, so that no credentials are sent to the wrong cluster. On a mismatch the task fails with live_cluster_uuid and expected_cluster_uuid in its result.

An empty value disables this identity guard, and a module that logs in warns.

If not set, the value of the QUMULO_EXPECTED_CLUSTER_UUID environment variable is used.

idmap_domain

string

The NFSv4 ID-mapping domain. An empty string clears it.

krb5_enabled

boolean

Accept Kerberos authentication (krb5).

Choices:

  • false

  • true

krb5i_enabled

boolean

Accept Kerberos with integrity checking (krb5i).

Choices:

  • false

  • true

krb5p_enabled

boolean

Accept Kerberos with privacy (krb5p).

Choices:

  • false

  • true

request_timeout

integer

Seconds to wait for one HTTP response.

If not set, the value of the QUMULO_REQUEST_TIMEOUT environment variable is used.

Default: 60

retry_timeout

integer

Seconds to keep retrying a request that is safe to resend, after a lost connection or an HTTP 502, 503 or 504.

If not set, the value of the QUMULO_RETRY_TIMEOUT environment variable is used.

Default: 300

state

string

present makes sure the settings are as declared. With tenant it creates the tenant’s override when it has none, even with no settings declared, in which case the override holds the global settings’ current values, and otherwise changes only the settings that differ.

inherit removes the tenant’s override, so that the tenant uses the global settings. It needs tenant, the settings options are not used with it, and it changes nothing when the tenant has no override.

A tenant has no override only when the cluster answers api_nfs_tenant_settings_do_not_exist_error; any other error answer to the read of the override fails the task (QUIRK-112).

Choices:

  • "present" ← (default)

  • "inherit"

tenant

string

The tenant whose override of the NFS server settings the task manages, by name, compared exactly. Unset, the task manages the global settings.

With a tenant, the settings options describe that tenant’s override. A new override is created with a PUT whose body is the global settings document as the cluster returns it, with the declared options over it, so a setting that this module does not model keeps its global value. An existing override keeps the values of the options left unset.

Turning v4_enabled on in the override, which includes creating an override that has it on, first looks for two of the tenant’s export paths where one is inside the other, in check mode too. The task fails naming the pair. state=inherit looks the same way when the global settings have NFSv4.1 on and the override has it off (QUIRK-114). Only this tenant’s exports are looked at, and none for a tenant that an earlier task creates, which holds no export yet.

Outside check mode, a name that no tenant has fails, and the message lists the tenants. In check mode such a name is taken as a tenant an earlier task creates, so the task reports a change with a note in notes. With state=inherit such a name is satisfied, and the task changes nothing.

Needs the tenant list, which needs PRIVILEGE_TENANT_READ.

v4_enabled

boolean

Serve NFSv4.1 as well as NFSv3.

The cluster refuses to turn NFSv4.1 on while one export’s path, the path clients mount (export_path), is inside the path of another export of the same tenant, as /data/projects is inside /data. Only export paths count, not the directories the exports serve, so exports at /a and /b may serve / and /x. Export paths of different tenants are not compared, so one tenant’s export at / and another’s at /home do not count. The export at / that a newly formed cluster has contains every other export of its tenant.

When the task turns NFSv4.1 on for the global settings, the module looks for such a pair first, in check mode too, in every tenant, one whose override keeps NFSv4.1 off included, as the cluster’s own check does, and fails naming the first pair it finds. With tenant, the module looks only at that tenant’s exports, as tenant describes.

Choices:

  • false

  • true

validate_certs

boolean

Verify the cluster’s TLS certificate.

If not set, the value of the QUMULO_VALIDATE_CERTS environment variable is used.

Choices:

  • false

  • true ← (default)

Notes

Note

  • API: without tenant, GET and PATCH /v2/nfs/settings, and GET /v3/nfs/exports/ before turning NFSv4.1 on. With tenant: GET /v1/multitenancy/tenants/, which needs PRIVILEGE_TENANT_READ; GET, PATCH (If-Match) and DELETE (If-Match) /v1/multitenancy/nfs/settings/{tenant_id}; PUT to the same route, without If-Match, to create the override, with the global settings document as the cluster returns it and the task’s options over it (QUIRK-113, QUIRK-115); GET /v2/nfs/settings for that document, and before an inherit; and GET /v3/nfs/exports/ for the nesting check of tenant.

  • The global settings route returns no ETag, so a change another client makes between the module’s read and its write is overwritten. The PATCH of a tenant’s override carries the If-Match of its read.

  • tenant resolves through the multitenancy REST API, which Qumulo marks as preview; a later Qumulo Core release may change it.

  • The Kerberos flavours work only once the cluster is joined to Active Directory, or holds a standalone KDC’s keytab (qumulo.cluster.kerberos_keytab), and its DNS and time agree with the KDC’s.

Examples

# These tasks carry no connection options. Set them once for the play with module_defaults for
# group/qumulo.cluster.qumulo, or in the QUMULO_* environment variables.
- name: Serve NFSv4.1 with Kerberos privacy only
  # The cluster refuses NFSv4.1 while one export's path is inside another's in the same tenant, and the factory export
  # of / contains every other export of its tenant. Remove or replace it first with qumulo.cluster.nfs_export.
  qumulo.cluster.nfs_settings:
    v4_enabled: true
    auth_sys_enabled: false
    krb5_enabled: false
    krb5i_enabled: false
    krb5p_enabled: true
    idmap_domain: corp.example.com

- name: Turn NFSv4.1 on after replacing the factory export of / with exports that do not nest
  # The module names a pair of nested export paths and fails before it writes. Remove one of the pair, or give the
  # inner one a path outside the outer one.
  block:
    - name: Export the project tree at its own path
      # While NFSv4.1 is off, the cluster accepts this export inside the export of /.
      qumulo.cluster.nfs_export:
        export_path: /projects
        fs_path: /data/projects
        restrictions:
          - host_restrictions: [10.20.0.0/16]

    - name: Remove the factory export of /
      qumulo.cluster.nfs_export:
        export_path: /
        state: absent

    - name: Serve NFSv4.1
      qumulo.cluster.nfs_settings:
        v4_enabled: true

- name: Accept Kerberos with integrity checking as well
  qumulo.cluster.nfs_settings:
    krb5i_enabled: true

- name: Set the NFSv4 ID-mapping domain
  qumulo.cluster.nfs_settings:
    idmap_domain: corp.example.com

- name: Preview turning NFSv4.1 on
  qumulo.cluster.nfs_settings:
    v4_enabled: true
  check_mode: true
  diff: true
  register: nfs_preview

- name: Show the settings that would change
  ansible.builtin.debug:
    msg: "{{ nfs_preview.diff.before }} -> {{ nfs_preview.diff.after }}"
  when: nfs_preview.changed

- name: Go back to NFSv3 with AUTH_SYS, and clear the ID-mapping domain
  qumulo.cluster.nfs_settings:
    v4_enabled: false
    auth_sys_enabled: true
    idmap_domain: ""

- name: Preview turning NFSv4.1 on for the eng tenant only
  # The new override holds the global settings as the cluster has them now, with v4_enabled changed. The diff shows {}
  # for before, since the tenant has no override yet, and the full override for after. The task fails, in check mode
  # too, when two of the eng tenant's export paths nest, and names them. The other tenants' exports are not looked at.
  qumulo.cluster.nfs_settings:
    tenant: eng
    v4_enabled: true
  check_mode: true
  diff: true
  register: eng_nfs_preview

- name: Show the override the eng tenant would get
  ansible.builtin.debug:
    var: eng_nfs_preview.diff.after
  when: eng_nfs_preview.changed

- name: Serve NFSv4.1 to the eng tenant only
  # The first run creates the override, from the global settings with v4_enabled changed. A second run changes nothing.
  qumulo.cluster.nfs_settings:
    tenant: eng
    v4_enabled: true

- name: Let the eng tenant use the global NFS settings again
  # Removes the eng tenant's override. When the global settings have NFSv4.1 on and the override has it off, the task
  # first looks for nested export paths in the eng tenant and fails naming them. When the tenant has no override, the
  # task changes nothing.
  qumulo.cluster.nfs_settings:
    tenant: eng
    state: inherit

Return Values

Common return values are documented here, the following are the fields unique to this module:

Key

Description

diff

dictionary

The settings before and after the task, with the option names above.

With tenant, each side is the tenant’s override with every setting, and {} for a side where the tenant has none. In check mode, the after of a create is the global settings the cluster holds now with the declared options changed.

Returned: when the task runs with diff mode on

after

dictionary

The settings after the task.

Returned: success

after_header

string

The label of the after side: tenant and the tenant’s name.

Returned: with tenant

Sample: "tenant eng"

before

dictionary

The settings before the task.

Returned: success

before_header

string

The label of the before side: tenant and the tenant’s name.

Returned: with tenant

Sample: "tenant eng"

expected

dictionary

The values the module wrote, for the options the read-back after the write did not return as written.

Returned: on a failure when the read-back after a write differs from what was written, except after a lost connection, which returns maybe_applied instead

Sample: {"idmap_domain": "corp.example.com"}

maybe_applied

boolean

True when a write was sent and the read-back did not confirm it. The module fails with changed true.

Returned: on such a failure

Sample: true

nfs_settings

dictionary

The settings after the task, with the option names above.

In check mode they are the settings the task would leave.

With tenant, they are the tenant’s override, with every setting, and an empty dict after state=inherit.

Returned: always

Sample: {"auth_sys_enabled": true, "idmap_domain": "", "krb5_enabled": true, "krb5i_enabled": true, "krb5p_enabled": true, "v4_enabled": false}

notes

list / elements=string

What the module noticed, such as, with tenant in check mode, a tenant that does not exist yet, or a write it confirmed by reading back after the connection was lost.

Returned: when there is something to note

Sample: ["tenant 'finance' does not exist yet; an earlier task is expected to create it"]

observed

dictionary

The values the cluster returned on that read-back, for the options in expected.

Returned: on a failure when the read-back after a write differs from what was written, except after a lost connection, which returns maybe_applied instead

Sample: {"idmap_domain": ""}
