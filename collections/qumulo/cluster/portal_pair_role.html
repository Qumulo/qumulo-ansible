qumulo.cluster.portal_pair role – Pair a spoke cluster with a hub cluster through a portal, or drain and decommission the pairing

Note

This role is part of the qumulo.cluster collection (version 0.1.0).

It is not included in ansible-core. To check whether it is installed, run ansible-galaxy collection list.

To install it use: ansible-galaxy collection install qumulo.cluster.

To use it in a playbook, specify: qumulo.cluster.portal_pair.

Entry point main – Pair a spoke cluster with a hub cluster through a portal, or drain and decommission the pairing

New in qumulo.cluster 0.1.0

Synopsis

  • Reaches both clusters from one host, with one set of connection options for each, so it runs once per pairing. Each set is what module_defaults for group/qumulo.cluster.qumulo takes, and must name its cluster’s UUID in expected_cluster_uuid. The pairing is identified by the two UUIDs.

  • With portal_pair_state=present, checks that both clusters run the same Qumulo Core version, proposes the portal and its roots on the spoke with qumulo.cluster.portal_spoke, accepts it and authorizes the roots on the hub with qumulo.cluster.portal_hub, and waits until both sides are ACCEPTED and ACTIVE with every root authorized. Roots proposed outside portal_pair_roots are left as they are, and not waited for. A second run changes nothing.

  • With portal_pair_state=absent, drains the spoke first by setting the portal’s type to read-only on the hub and waiting until both sides show it, then deletes the spoke portal and waits until the hub portal is gone too. A portal whose spoke is DISCONNECTED cannot be drained, and its deletion needs portal_pair_allow_data_loss; without it, the role fails before any change when the hub sees the spoke DISCONNECTED. A PENDING portal holds no spoke writes and is deleted without a drain.

  • Removing only the hub’s record of a spoke that no longer exists, such as an edge rebuilt with a new UUID, is qumulo.cluster.portal_hub with state=absent; this role needs both clusters.

  • Under --check, predicts each side’s change and waits for nothing.

  • Sets the fact portal_pair_portals to the portal as each side reports it, in the shape qumulo.cluster.portal_info uses, under spoke and hub; after a decommission both are null.

Parameters

Parameter

Comments

portal_pair_allow_data_loss

boolean

Allow deleting a portal whose other side is DISCONNECTED, which forces the delete and loses spoke writes the hub has not received.

Choices:

  • false ← (default)

  • true

portal_pair_hub

dictionary / required

Connection options for the hub cluster, as for portal_pair_spoke.

portal_pair_hub_hosts

list / elements=dictionary

The hub’s IP addresses, as the spoke reaches them, each with address and an optional port, 3713 by default. Needed with portal_pair_state=present.

The role takes them as given and never derives them from the cluster’s network status.

portal_pair_roots

list / elements=dictionary

The roots to propose and authorize, each with spoke_root, a path that must not exist on the spoke yet, and hub_root, an existing directory on the hub.

Default: []

portal_pair_spoke

dictionary / required

Connection options for the spoke cluster, such as api_host, api_password and expected_cluster_uuid.

portal_pair_spoke_hosts

list / elements=dictionary

The spoke’s IP addresses, as the hub reaches them, in the form of portal_pair_hub_hosts. Needed with portal_pair_state=present.

portal_pair_state

string

Whether the pairing exists.

Choices:

  • "present" ← (default)

  • "absent"

portal_pair_type

string

The portal’s type, read_write or read_only.

Choices:

  • "read_write" ← (default)

  • "read_only"

portal_pair_wait_timeout

integer

Seconds each wait may take, passed to the modules as their wait_timeout.

Default: 600
